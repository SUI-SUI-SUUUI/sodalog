## 1. 設計原則 【最新】

1. 記録するために育てるのではなく、育てることを助けるために記録する。
2. 場所を記録の主語とする。
3. 植物は必要なときだけタグとして記録する。
4. 人間に入力させなくていい情報は、できるだけ入力させない。
5. 「記録する」は速度を優先する。
6. 「アルバム」は振り返りや写真表示を優先する。
7. 写真共有を前提としない。
8. 将来機能のために、現在の記録体験を複雑にしない。

## 2. 基本コンセプト 【最新】

そだログは、「記録するために育てるのではなく、育てることを助けるために記録する」ことを基本思想とする。

- 園芸作業中に細かな入力を要求せず、できるだけ短い操作で記録を残せることを優先する。
- 「人間に入力させなくていい情報は、できるだけ人間に入力させない」ことを設計原則とする。
- 入口はLINE。LINE公式アカウントのリッチメニュー「そだログを開く」からLIFFを開き、「アルバム」「記録する」「相談」の3機能を画面上部で切り替えて使う（5.4節・12.10節）。「相談」は準備中の表示にとどめる。
- 当面は開発者本人だけが使う（2.2節・12.2節）。

### 2.4 実利用フェーズでの優先順位 【最新】

機能の数を増やすことより、次を優先する（上ほど優先）。

1. **写真と記録がきちんと残る**：保存に失敗しない、失敗したら分かる、再送しても重複しない（6.3節・12.4節）。実データを失わない（12.8節）。
2. **記録が簡単にできる**：LINEから1タップで開き、場所タイル → 記録画面 → 保存の短い流れで終わる（12.10節・6章）。
3. **庭仕事の途中でも使いやすい**：片手・屋外・手が汚れている・通信が弱い状況で迷わない。待ち時間が短い。
4. **過去の記録を見返しやすい**：場所ごと・年ごとのアルバム（8章）。
5. **自分が続けて使える**：使っていて面倒に感じた点を記録し、小さく直す（16.2節）。

- 改善の材料は、実際に使って気づいたこと（不便・迷い・待ち時間・失敗）とする。気づいたことは仕様書の16.2節「実利用で気づいたこと」に書き留め、直すかどうかはまとめて判断する。
- 新しい機能（相談、通知など）は、上の5つに問題がないと分かるまで着手しない。

## 3. 記録単位 【最新】【過去から変更】

記録の主語は「植物」ではなく「場所」とする。

場所の例：北側花壇／南側花壇／玄関／ベランダ／室内

植物は場所に付随する任意の「タグ」として扱う。

```
場所：北側花壇
作業：剪定
植物タグ：アジサイ、ホスタ
```

- 植物の選択は必須にしない。
- 植物タグを付けない記録は「その場所全体に対する記録」とみなす。
- 「全体」という専用の植物タグは作らない。
- 1件の記録に植物タグを0〜複数付けられる。

**過去から変更**：旧仕様では「1件の記録＝1つの場所＋1つの植物」を前提にしており、植物名の入力欄は1つだけだった。デモデータには「全体」という仮の植物名が使われていた。

### 3.1 植物タグの保存形式 【最新】

- JSON配列の文字列で保存する（例：`["アジサイ","ホスタ"]`）。
- タグなしは `[]` とする。
- 区切り文字方式（「、」「,」など）は、値そのものに記号が含まれると壊れるため採用しない。
- 1つのタグは**20文字まで**（絵文字も1文字と数える）、1件の記録につき**最大10個**とする。
- 保存前に、各タグを**NFKC正規化**し、**前後の空白を除去**する（場所名と同じ扱い、12.6節）。空のタグと重複したタグは除く。

### 3.2 植物タグの入力UI 【最新】【保留】

- 【最新】自由入力のみとする。入力欄に名前を入れて「追加」（またはEnter）でタグになり、入力欄の中に並ぶ。×で外せる。
- 【最新】保存するとき、入力欄に残っている名前もタグとして一緒に保存する。
- 【保留】過去に使ったタグの候補表示、よく使うタグの表示、タグのID管理は、実際に使ってから検討する。

## 4. 詳細場所 【最新】【過去から変更】

「北側花壇 ＞ 東側」「北側花壇 ＞ 中央」のような、場所の下位にある「詳細場所」は廃止する方向とする。

理由：

- 入力項目を増やさないため
- Driveやデータ構造を必要以上に複雑にしないため
- 園芸記録を続けやすくするため

細かく分けたい場合は、場所名そのものを分けて登録する（例：「北側花壇・東」）。

- 新しい記録シート（12章）には詳細場所の列を設けない。
- **既存の `garden_log` の詳細場所列と、そのデータは削除しない**（12.8節）。

**過去から変更**：旧仕様では「場所（庭／室内／その他）×詳細場所（北側／南側／中央／東側／西側）」の固定2段選択だった。写真のDriveフォルダも「場所/詳細場所/年」の階層だった。

## 5. 場所選択UI 【最新】【過去から変更】

### 5.1 場所名のコラージュ風タイル 【最新】

場所選択画面は、**場所名だけをタイル状に配置したコラージュ風UI**とする（「記録する」と「アルバム」で同じ画面を使う。5.4節）。これは保留事項ではなく、現時点の採用方針である。

「写真を並べたコラージュ」ではなく、「場所名をタイル状に配置したコラージュ風UI」を意味する。

```
┌──────────────┐
│   北側花壇    │
├──────┬───────┤
│南側花壇│ 玄関 │
├──────┴───────┤
│     室内      │
└──────────────┘
```

- 場所選択画面では画像を読み込まない。画像を非表示にするだけでなく、この画面のための画像取得処理そのものを行わない。
- 場所タイルをタップすると、その場所を選択した状態で記録画面へ進む（「アルバム」を選んでいるときは、その場所のアルバムへ進む。5.4節）。
- 場所名が読みやすく、タップしやすいことを優先する。
- 前回表示した場所の一覧を端末に覚えておき、画面を開いたらまずそれを表示する。最新の一覧は裏で取得し、届いたら差し替える。

**タイルの配置・見た目**（STEP 4-2の直前に決定）：

- 登録順のまま、「1件（全幅）」と「2件（横に50:50）」のグループを交互に並べる。
- 2件のグループに1件しかないときは、その1件を一時的に全幅で表示する。場所を追加しても変わるのは最後のグループだけで、**既存のタイルの位置は変わらない**（5.2節）。
- タイルの色は、場所IDから決まる淡い色（8色）で固定する。同じ場所はいつも同じ色になる。
- 場所名の長さでタイルの大きさは変えず、文字の大きさで調整する（6文字まで・12文字まで・それ以上の3段階）。

### 5.2 場所タイルの並び順 【最新】

- **登録順で固定表示する**（先に登録した場所が先頭、新しく登録した場所は末尾に追加）。
- 「最近使った順」は場所の並びには採用しない。

理由：ユーザーが場所タイルを「画面上の位置」で覚えて選べることを優先するため。使うたびに位置が変わると、かえって選びにくくなる可能性がある。

**過去から変更**：旧仕様（STEP 8）では、「最近使った場所」を3〜5件、代表写真付きのカードで並べる方針だった。これは本番で実装・稼働している（16.3節）。新方針では「最近使った場所」を場所選択の仕組みとしては採用しない。

### 5.3 場所の登録 【最新】

- 場所選択画面の下に、控えめな「＋ 場所を追加」ボタン（点線）を置く。押すと場所名の入力欄が開く。
- 場所が1件もないときは、タイルの代わりに「最初の場所を登録しましょう」という登録フォームだけを表示する（10章）。
- 入力するのは場所名だけ。写真・方角・詳細場所は求めない（10章）。
- 場所名のルール（20文字まで・NFKC正規化・前後の空白除去）は12.6節のとおり。画面でも同じルールで事前に確認し、最終的な判定はサーバーが行う。
- 登録した場所は、そのまま選択した状態にする（10章「最初の場所を登録したら、そのままその場所での記録に進める」）。
- 同じ名前の場所がすでにある場合は新しく作らず、既存の場所を選択した状態にする（12.6節）。

### 5.4 3機能の切り替え（上部ナビ）と、アルバム側の場所選択 【最新】

STEP 4-4b で決定（検討の経緯は `docs/design/navigation-board.html` の Round 1〜4。採用したのはC案）。

**上部ナビ**

- 画面上部に、左から「**アルバム → 記録する → 相談**」の3つを並べる（左から 過去 → 今 → 次 の順）。
- 各項目は、丸いアイコンとその下の短い機能名で示す。丸の中心どうしを線でつなぐ（相談へは点線）。
- 丸は3つとも**同じ大きさ（直径60px）**とする。
  - アイコン画像は、用意した3つの個別画像の絵の部分だけを使う（正方形・背景透過・128px）。元画像の緑の外枠は使わない。
  - 外枠と選択状態は画面側（CSS）で表す。選択中は緑の太い輪、選択していない項目は控えめな灰色の輪で、少し色を落とす。
- ナビを置くのは**場所選択画面とアルバム画面**とする。記録画面（6.3節）には置かない。
- 機能名はナビに出ているため、画面の見出しで機能名を繰り返さない。
  - 場所選択画面の見出しは、どちらの機能でも「場所を選ぶ」とする。説明文だけを「記録する場所を選んでください」「振り返る場所を選んでください」と変える。
  - アルバム画面には「アルバム」の見出しを置かない。
- 最初に開いたときは「記録する」を選んだ状態とする。
- **相談**は準備中とする。白黒・点線の輪で表示し、丸の下の縁に「準備中」を重ねる。押しても画面は変えず、ナビの下に「相談は準備中です」の案内を出す（「閉じる」か5秒で消える）。

**アルバム側の場所選択**

- 「アルバム」を選ぶと、場所選択画面のタイル（5.1節と同じ配置・色）を押したときの行き先がその場所のアルバム（8.2節）になる。
- アルバム側のタイルには、場所名の下に、その場所の**総記録数**（写真あり＋写真なし、例：「12件」）を表示する。記録する側のタイルには表示しない。
  - 件数は、場所ごとにアルバムを取得せず、場所一覧を件数付きで1回取得して得る（`GET /api/locations?include=counts`、12.12節）。数え方はアルバムの `total` と同じ（8.1節）。
  - 件数を取得できなかったときは、件数なしでタイルを表示し、操作はそのまま続けられる。
  - 記録を保存したら件数を取り直す。
- 場所の登録（5.3節）は記録する側だけで行う。アルバム側で場所が1件もないときは、「まだ場所がありません。『記録する』から場所を登録してください。」と表示する。

## 6. 記録画面 【最新】

- 「記録する」は速度を最優先する。
- 場所を選択したあとは、できるだけ1画面で記録を完了できるようにする。
- 場所は必須、それ以外は原則任意とする。任意項目の候補は、作業内容・植物タグ・写真・メモ。
- **記録の成立条件**：場所＋（写真・作業内容・植物タグ・メモのどれか1つ以上）。場所だけの空の記録は保存しない。
- 詳細場所の入力は求めない（4章）。
- 場所の代表写真は持たない（7章）。
- 記録画面では、場所の写真も過去の記録写真も読み込まない。
  - 今回の記録に添付する写真の選択・プレビュー・保存は記録機能に含む。
- 園芸作業中でも迷わず入力できることを優先する。
- メモは**300文字まで**とする。改行は使える。本人が書いた文は変換せず（NFKC正規化はしない）、前後の空白だけ除く。

### 6.1 作業日 【最新】

- 作業日の入力欄は維持し、初期値は今日とする。手で変更できる。
- 作業日は**実在する日付で、日本時間の今日以前**とする。未来の日付は保存しない。
- 過去の日付は、さかのぼりの制限を設けない。
- 変更は画面内のカレンダーで行う（6.3節）。日付を押しただけでは決まらず、「この日にする」で決定する。
- 過去の写真を登録するときは、作業日を手で直す（12.9節）。
- 撮影日時（EXIF）から作業日を提案する機能は必須にしない【将来】。

### 6.2 作業内容 【最新】【保留】

- 【最新】作業内容は任意で、複数選択できる。JSON配列で保存し、未選択は `[]`。
- 【最新】選べる作業内容は**次の9項目のみ**とする（この順で表示・保存する）：水やり／草取り／肥料／剪定／植え付け／植え替え／成長記録／収穫／撤去。これ以外の値は保存しない（項目は後から追加できる）。
- 【最新】「その他」は使わない。
- 【最新】作業チップは上の**決まった順で固定**し、3列×3行に並べる（いつも同じ位置で押せるようにするため）。保存するときも、選んだ順ではなくこの順に並べ替える。
- 【保留】場所ごとの使用頻度順に並べるかどうかは、実際に使って必要性を確かめてから検討する。

**過去から変更**：旧仕様（現在の本番）の作業内容は、水やり／肥料／収穫／剪定／草取り／植え付け／その他の7項目で、作業チップは場所ごとの使用頻度順に並ぶ（STEP 10で実装）。

### 6.3 記録画面の構成と見た目 【最新】

場所タイルを押したあとの記録画面は、上から次の順とする（STEP 4-3b で決定。検討の経緯は `docs/design/record-screen-board.html` の Round 1〜5）。

1. **場所**（上部の帯）：場所名と「場所を変える」
2. **作業日**：横長の枠
3. **写真**：画面幅・縦横比4:3の「写真を撮る・選ぶ」枠
4. **作業内容**：9項目を3列×3行（6.2節）
5. **「植物・メモを書く」**：初めは閉じている。開くと植物の入力とメモ欄が出る
6. **保存**：画面の下に固定

- **場所の色**：記録画面全体を、その場所のタイルの色（5.1節）と同じ色相の淡い濃淡で統一する（ライトモードのみ）。
  - 場所帯・写真枠・選択中の作業・「植物・メモを書く」の内側に使う。
  - 保存ボタンと作業日の「変更」は、その場所色で最も濃い色に白文字とする。
  - 場所タイルの8色それぞれに濃淡の組を用意する。白文字を載せる色は、白との明るさの差（コントラスト比）4.5以上とする。
- **場所名**：2行まで。長さに応じて文字を小さくする（8文字まで・14文字まで・それ以上の3段階）。「場所を変える」は折り返さず1行に固定する。
- **作業日**：枠の左に「作業日 2026/09/27（今日）」、右に塗りつぶしの「変更」ボタンを置く。枠のどこを押しても、同じカレンダーが開く。
- **作業日のカレンダー**：画面の下から出る、画面の横幅いっぱいのシートとする。
  - 上部に選んでいる日を大きく表示する。
  - 月を切り替えられる。今月より先の月へは進めない。
  - 今日は枠線と「今日」の文字、選んでいる日は場所色の塗りつぶしで示す。
  - 未来の日は押せない。「今日にする」ですぐ今日に戻れる。
  - 「この日にする」で決定する。「閉じる」「キャンセル」・背景を押すと、元の日付のまま閉じる。
- **写真**：選ぶと枠の中に表示し、「変える」「外す」を写真の上に重ねる。写真の準備中（縮小・圧縮中）は「写真を準備しています…」と表示し、保存ボタンは押せない。
- **「植物・メモを書く」**：閉じているときも、入力済みなら「植物1・メモあり」のように表示する。
- **保存欄**：左に入力内容の要約（例：「水やり・剪定・写真1枚・植物2・メモ」）、右に保存ボタンを置く。何も入力していないときは、保存ボタンを押せず、要約の位置に「どれか1つで保存できます」と表示する。
- **保存中・保存後**：
  - 保存ボタンを押したら、二重に押せないよう無効にして「保存しています…」と表示する（進み具合は出さない）。
  - 失敗したら、エラーを表示し、ボタンを「もう一度保存」にする。同じ記録IDのまま再送する（12.4節）。
  - 成功したら、場所タイルの画面に戻り、「『北側の花壇』に記録しました」のように知らせる。「同じ場所に続けて記録」は設けない。
- **入力途中で「場所を変える」を押した場合**：入力した内容が保存されないことを確認してから戻る。

## 7. 写真の扱い 【最新】【過去から変更】

- 場所ごとの「代表写真」は持たない。
  - 理由：場所選択画面で写真を読み込むと、その待ち時間で記録の開始が遅れ、ユーザーが記録そのものをやめてしまうおそれがあるため。
- 「記録する」と「アルバム」とで、UXの優先順位を分ける。
  - 記録する＝速度優先
  - アルバム＝写真による振り返り優先
- 日々の記録には、必要に応じて写真を添付する。
- 当面は**1記録1枚**とする。複数画像への対応は【保留／将来】とする（13章・14章）。
- 保存する写真の形式は**JPEGのみ**、1枚**3MBまで**とする。HEICなど他の形式は、LIFF側でJPEGに変換してから送る（12.9節）。
- 保存した写真の共有設定は変更しない。Driveの「一般的なアクセス」は**制限付き**のままとする（9章）。

**過去から変更**：旧仕様（STEP 8）では場所エンティティに `representativeImage`（その場所の最新の記録写真）を持たせ、場所カードに表示していた。写真は、記録を保存したあとにLINEのトークで送って紐付ける方式だった。

## 8. アルバム 【最新】

- 日々の記録写真を見て振り返る機能とする。
- 写真表示が主な目的なので、一定の画像読み込み時間は許容する。
- 記録画面では画像を読み込まず、アルバム画面では画像を使う、という役割分担とする。
- 場所写真の廃止を理由に、記録写真の取得やアルバム表示を削除しない。

### 8.1 新しいアルバムの方針 【最新】（STEP 4-4 で決定）

- アルバムの主軸は「**場所ごとに振り返る**」とする。流れは「場所を選ぶ → その場所の記録を見る」。
- 対象は新しい保存先の「記録」タブと `写真/<年>/` のデータだけとする。旧 `garden_log` の表示・統合・移行は扱わない（12.8節）。
- 場所ごとに、総記録数（写真あり＋写真なし）を示す。
- **年で切り替える**。年の一覧は、写真フォルダの年ではなく、その場所の記録の**作業日の年**から作る。最初はいちばん新しい年を表示する。「すべての年」はまだ設けない。
- 年を選ぶと、その年の写真あり記録と写真なし記録の両方を表示する。
- **写真あり記録**は、写真を並べて見せる。古い順（画面の左が過去、右が最新）。
- **写真なし記録**は、写真とは分けて表で見せる。新しい順（表の上が最新）。
- 作業日が同じ記録は、記録日時の順で並べる。
- 1回に表示するのは、写真あり・写真なしそれぞれ**1年あたり最大300件**とする。超えた場合は古い記録を省き、一部だけを表示していることを利用者に分かるようにする。
- 写真の共有設定は変えない（「制限付き」のまま。9章）。写真はサーバーを通して、本人確認をしたうえで取得する（12.12節）。
- 画面の構成と見た目は8.2節のとおり。

### 8.2 アルバム画面の構成と見た目 【最新】

場所タイル（5.4節）を押したあとのアルバム画面は、上から次の順とする（STEP 4-4b で決定。検討の経緯は `docs/design/album-screen-board.html` の Round 1〜3）。

1. **上部ナビ**（5.4節）
2. **場所の帯**：場所名・その場所の総記録数・「場所を変える」、その下に年ボタン
3. **写真**：写真あり記録の横並び
4. **写真なしの記録**：表

- **場所の色**：記録画面（6.3節）と同じく、その場所の色の淡い濃淡で画面全体をそろえる。
- **場所名**：2行まで。右に総記録数（例：「27件」）を小さく添える。
- **「場所を変える」**：白背景・角丸・細い枠の小さなボタン（文字14px）とする。記録画面の「場所を変える」も同じ見た目にそろえる。押すと場所選択画面に戻る。
- **年ボタン**：作業日の年ごとに「2026 10件」の形で並べ、左が過去・右が最新とする。選んでいる年は場所色の濃い色で塗る。最初はいちばん新しい年を選び（8.1節）、右端が見える位置から表示する。年が多いときは横にスクロールする。
- **写真の並び**：
  - 写真は**正方形のタイル**とし、写真の中央を切り抜いて表示する（縦長・横長のどちらも同じ枠）。
  - タイルの幅は**画面幅の約62%（最大322px）**とする。画面に約1.5枚が見え、右（または左）にも写真があることが分かるようにする。
  - **横スクロール**で送る。左が過去・右が最新で、開いた直後と年を変えたときは右端（最新）から表示する。
    - 指のスワイプとトラックパッドは、ブラウザの標準の動きのままとする。
    - マウスはホイールとドラッグで送る。
    - 端にまだ写真があるときは、その端を背景色にぼかして示す。
  - 見出しは「写真」、その右に「5枚・右が最新」のように枚数を示す。写真の下に「← 左が過去　右が最新 →」と表示する。
  - タイルの左上に作業日（月/日）を表示する。作業内容・植物・メモのどれかがある記録には、右下に ⓘ を表示する。
  - 写真の読み込み：
    - 一覧ではサムネイル（12.12節 `size=thumb`）を使い、見えてきた写真から順に、同時に4枚まで読み込む。
    - 届くまでは淡い場所色の枠を表示する。
    - 読み込めなかった写真は、その枠に「写真を読み込めませんでした」と表示する。
- **記録の詳細（写真の拡大表示）**：
  - 写真のどこを押しても、画面の下から詳細のシートを開く。
  - 先にサムネイルを表示して「高画質を読み込み中…」を重ね、元画像（`size=full`）が届いたら差し替える。
  - 写真の下に、作業日・作業内容・植物・メモを表示する。値がない項目は「なし」とする。
  - 「閉じる」・背景を押すと閉じる。
- **写真なしの記録**：
  - 見出しは「写真なしの記録」、その右に「5件・上が最新」のように件数を示す。
  - 表の列は、作業日・作業内容・植物・メモとし、新しい順に並べる（8.1節）。
  - 作業日の列は左端に固定する。表が画面幅に収まらないときは、表の枠の中で横にスクロールする。
  - 値がない欄は「—」とする。
- **件数の上限を超えたとき**：写真あり・写真なしそれぞれ、「この年は写真が多いため、新しい300件だけを表示しています。」のように知らせる（8.1節）。
- **記録がないとき**：
  - その場所に記録が1件もなければ、「この場所の記録はまだありません。『記録する』から記録すると、ここで振り返れます。」と表示する。
  - 選んだ年に写真（または写真なしの記録）がなければ、その欄に「この年の写真はありません」などと表示する。
- **読み込みの失敗**：エラーの内容と「もう一度読み込む」を表示する。認証が切れた場合は「LINEの認証が切れました。LINEから開き直してください。」と表示する。
- 記録を保存したら、その場所のアルバムは次に開いたときに取り直す。
- **文字の大きさ**：iPhone実機での確認のあと、補足の文字を大きくし（主に13〜15px）、灰色の補足文字の色を濃くした。主な値は次のとおり。
  - 見出し「写真」「写真なしの記録」は14px、その右の件数は13px。
  - 「← 左が過去　右が最新 →」は13px。
  - 表の列名は13px、表の中身は15px。
  - 年ボタンの件数は12px、場所タイルの件数は13px、写真の日付は13px、ナビの機能名は14px。

## 12. 技術方針（2026-09-25決定） 【最新】

### 12.1 全体構成

| 経路 | 構成 |
| --- | --- |
| 現行（本番稼働中） | LINE → Cloud Run（LINE署名検証）→ GAS（共有シークレット検証）→ `garden_log` シート・写真フォルダ（開発者のDrive） |
| 現行のLIFF | GitHub Pages（`liff/index.html`）→ `liff.sendMessages` でLINEへテキスト送信 → 上の経路で保存。アルバムはLIFFからGASの `action=list` / `action=image` を直接呼ぶ |
| **個人利用版（開発中、2026-10-02〜）** | LIFF → Cloud Run（LIFF IDトークンで本人確認）→ GAS（共有シークレット検証）→ **新しいスプレッドシート・Driveフォルダ**（12.13節） |
| 公開版の新方式（保留） | LIFF → Cloud Run のAPI → Google Drive API / Google Sheets API → 利用者本人のGoogle Drive上に、アプリが作成したフォルダ・シート |

- **2026-10-02 から、個人利用版の構成で開発する（12.13節）。** 以下の2項目と12.2・12.3節のOAuth・`drive.file` に関する内容は、公開版の新方式としての設計で、将来再開するときのために残す。
- 写真付きの記録保存は、Cloud Runに新しいAPIを作って行う（B案）。GASにLIFF用のアップロード処理は追加しない。【個人利用版では変更：Cloud RunのAPIが受け取り、GASが保存する（12.13節）】
- 最終的な構成（一般公開・複数ユーザー）は、Cloud Run（Node.js/TypeScript）＋ Google OAuth ＋ 利用者本人のDrive/Sheets とする。開発者のDriveに一般利用者の記録・写真を集めない。【保留】

### 12.2 認証

- **LINEユーザーの確認**：LIFFのIDトークンをサーバー側で検証してユーザーを特定する。クライアントから送られてきたユーザーIDは信用しない。
  - LIFFは `Authorization: Bearer <IDトークン>` を付けてCloud RunのAPIを呼ぶ。
  - Cloud RunはLINEの検証API（`/oauth2/v2.1/verify`）でトークンを確かめ、発行先（`aud`）がLIFFのLINEログインチャネルであることも確認する。
  - 本人確認は、リクエストの本文を読むより先に行う。未認証のリクエストの本文は解析しない。
  - 同じ画面の連続したリクエストで毎回LINEに問い合わせないよう、検証結果は最大5分（トークンの有効期限を超えない範囲）だけ覚えておく。
  - 開発者1人用の段階では、許可したLINEユーザー（開発者本人）以外は拒否する（12.2.1節）。複数ユーザーへの対応は【将来】として12.11節で扱う。
- **Google**：OAuthのスコープは `drive.file`・`openid`・`userinfo.email` の3つのみ。高機密スコープや制限付きスコープは使わない。
- **refresh token**：開発段階（利用者は開発者1人）ではSecret Managerに保存する。複数ユーザーに対応するときはユーザーごとに管理する（Firestoreを予定）【将来】。
- OAuthの公開ステータスが「テスト中」のときのrefresh tokenの有効期限は、公開版を再開するときに対処方法を決める【将来】。個人利用版では、日常利用の経路でOAuthを使わない（12.13節）。

#### 12.2.1 本人限定アクセス（認証・認可） 【最新】（2026-10-04決定）【一部要確認】

本人専用の実利用フェーズでは、**開発者本人のLINEアカウントだけ**がそだログの記録・写真・アルバムを扱えるようにする。「URLを知っていれば使える」状態にはしない。

**考え方**

| 段階 | 意味 | そだログでの方法 |
| --- | --- | --- |
| 認証（だれか） | リクエストしているLINEユーザーを確かめる | LIFFのIDトークンを、Cloud RunがLINEの検証APIで検証し、LINEユーザーID（`sub`）を得る（12.2節） |
| 認可（使ってよいか） | そのLINEユーザーにそだログの利用を許すか決める | 許可リスト（`ALLOWED_LINE_USER_ID`）に入っているLINEユーザーIDだけを通す。それ以外は403 |

- 認証と認可は分けて扱う。認可の判定（「このLINEユーザーIDを通すか」）は、各サーバーで**1か所の関数にまとめる**（Cloud Runは `requireLiffUser`、GASは `isAllowedLiffUser` / `isAllowedLineUser`）。各APIの処理の中で個別に判定しない。
- 守る対象は**データとAPI**である。画面（GitHub Pages上のHTML・JavaScript）は誰でも取得できる前提とし、画面には秘密情報を置かない。LIFF IDやCloud RunのURLは秘密情報として扱わない。

**流れ**

```
リッチメニュー「そだログを開く」
↓
LIFF起動（liff.init）
↓
LINEログイン（未ログインなら liff.login。LINEアプリ内では通常は自動）
↓
IDトークン取得（liff.getIDToken）
↓
Cloud Run の /api/* に Authorization: Bearer <IDトークン> を付けて呼ぶ
↓
Cloud Run：IDトークンを検証（aud がLINEログインチャネルであることも確認）→ LINEユーザーIDを得る
↓
許可リストにあるLINEユーザーIDか？
  ├ はい → 処理する（検証済みのLINEユーザーIDだけを以後の処理で使う）
  └ いいえ → 403。データは返さない
```

**動作の決まり**

- IDトークンがない・不正・期限切れ：401。画面は「LINEの認証が切れました。LINEから開き直してください。」と表示する（現行のとおり）。
- 許可していないユーザー：403。画面は「このアカウントでは利用できません。」と表示し、記録画面・アルバムには進ませない。LINE側の検証APIに問い合わせられない：502。
- 許可リストが未設定のときは、**全員を拒否する**（全員を許可する側に倒さない）。Cloud Runは `/api` 配下を503にする（12.12節）。GASは未許可として扱う（現行のとおり）。
- 写真（`GET /api/photos/:fileId`）も同じ本人確認を通してから返す。Driveの共有設定は「制限付き」のままとし、写真の公開URLは作らない（7章・9章）。
- LINE Webhook（トークでのメッセージ）も、GASで許可したLINEユーザー以外のイベントは返信・保存せずに終える（現行の `isAllowedLineUser`）。
- 管理用API（`/admin/*`）はLIFFとは別に、管理用トークンで守る（12.12節）。
- 個人利用版では、記録・写真の読み書きをGASが行う（12.13節）。GASの `action`（`handleCloudRunAction`）は、**Cloud Runが本人確認を済ませたあとにだけ**、共有シークレット付きで呼ぶ。LIFFからGASの `action` を直接呼ぶ経路は作らない。GASは共有シークレットが合わない呼び出しを処理しない。
- クライアントから送られたLINEユーザーIDは使わない（12.2節）。

**許可リストの持ち方**

- 現在は、同じLINEユーザーIDを次の2か所に持っている。値は一致させる。
  - Cloud Run：Secret Manager `allowed-line-user-id`（環境変数 `ALLOWED_LINE_USER_ID`）
  - GAS：スクリプトプロパティ `ALLOWED_LINE_USER_ID`（Webhook、旧LIFFの保存、旧アルバム）
- 許可するのは開発者本人の1人だけとする。追加の利用者（家族など）を許可するかどうかは、この仕様の範囲外とし、必要になったときに検討する【将来】。

**将来の複数ユーザー化を妨げないための決まり**（極端なハードコードを避ける）

- LINEユーザーIDをコードや画面に直接書かない。許可リストは設定（Secret Manager・スクリプトプロパティ）から読む。
- 認可の判定を1か所にまとめておき、将来「許可リスト（複数件）」や「利用者の登録状態」による判定に差し替えられるようにする。
- 認証が済んだ後の処理には、検証済みのLINEユーザーIDを渡す形を保つ（Cloud Runの `res.locals.lineUserId`）。今は保存先が1つ（GASが作る新しい保存先。12.13節）でも、将来は「LINEユーザーID → その人の保存先」を引く形に変えられるようにする（12.11節）。
- 「記録」タブ・「場所」タブにはLINEユーザーIDの列を設けない（保存先そのものを利用者ごとに分ける方針のため。12.4節・12.11節）。

**【要確認】**（確認してから決める。13.1節）

1. （Q1）正式な入口で使うLIFFアプリ（本番LIFF `2010871516-DJ2YSRIw` に新しい画面を載せるか、検証用LIFFを使うか。12.10節）。どちらでも、IDトークンの `aud` が同じLINEログインチャネルであることを実機で確かめる。
2. （Q2）追加の防御として、次を行うかどうか。どちらも本人限定の仕組み（上記）とは別の「二重の鍵」であり、なくても本人限定は成り立つ。
   - LINEログインチャネルを「開発中」のままにして、チャネルの権限を持つ人だけがLIFFにログインできるようにする（チャネルの公開状態を変えると、本番LIFFの既存の動作にも影響するため、現在の状態の確認から行う）。
   - リッチメニューを全員向けではなく、開発者のLINEユーザーにだけ紐付ける（開発者以外には「そだログを開く」を見せない）。
3. （Q3）許可リストを、将来の複数件対応を見すえて「カンマ区切りで複数のIDを書ける形式」に今のうちに変えるか（今は1件のまま。変える場合はCloud RunとGASの両方を同時に変える）。

### 12.3 保存先

> 2026-10-02 以降、この節の `drive.file` による保存先は公開版の新方式として保留している。個人利用版の保存先は12.13節を参照。ここで作ったテスト用の保存先は削除せずに残す。

- **正式な保存先は、アプリが `drive.file` で新しく作成するフォルダとスプレッドシート**とする。
- `drive.file` では、アプリが作っていない既存の `garden_log` と写真フォルダにはアクセスできない（2026-09-25に実測。404 notFound）。一方、アプリが作ったファイルへの作成・追記・読み取りはできる（同日に実測）。
- 作成したファイルは、Driveの非公開メタデータ（`appProperties`）で見分ける。
- **検証中はテスト用の保存先を使う**（フォルダ「そだログ（テスト）」、スプレッドシート「そだログ記録（テスト）」）。本番用の保存先は、正式に切り替えるときに作成する。
- スプレッドシートには「記録」タブ（12.4節）と「場所」タブ（12.6節）を置く。どちらも初回セットアップ（12.12節）で作成し、すでにあるタブは作り直さない。
- 保存先フォルダの中に「写真」フォルダを置き、記録の写真を保存する（12.5節）。これも初回セットアップで作成する。

```
そだログ（テスト）/            … 保存先フォルダ
├─ そだログ記録（テスト）      … スプレッドシート（「記録」タブ・「場所」タブ）
└─ 写真/
   └─ 2026/                   … 作業日の年
      └─ 2026-09-27_北側花壇_<記録ID>.jpg
```

### 12.4 記録シート「記録」タブ 【最新】

| 列 | 見出し | 内容 |
| --- | --- | --- |
| A | 記録ID | 保存時にLIFFが作る一意のID（`crypto.randomUUID()` の形式）。重複保存の防止に使う |
| B | 記録日時 | サーバーが保存した日時 |
| C | 作業日 | 作業した日（手で変更できる） |
| D | 場所ID | 「場所」タブのID |
| E | 場所名 | 記録した時点の場所名。LIFFから送られた値は使わず、サーバーが「場所」タブから引く |
| F | 植物タグ | JSON配列。タグなしは `[]` |
| G | 作業内容 | JSON配列。未選択は `[]` |
| H | メモ | 自由記述 |
| I | 写真ファイルID | DriveのファイルID。写真がなければ空欄。1記録1枚 |
| J | 記録元 | 当面は `liff` |
| K | 更新日時 | 空欄の列として用意。修正機能は未実装 |
| L | 削除日時 | 空欄の列として用意。取り消し（論理削除）機能は未実装 |

- 書き込みは `valueInputOption=RAW` で行い、入力値が数式として実行されたり、日付型へ自動変換されたりしないようにする。
- 見出し行が想定と違う場合は、自動で直さずにエラーにする（手作業の編集で列がずれたときにデータを守るため）。
- **同じ記録IDの記録がすでにある場合は、新しく保存せず、既存の記録を返す**。通信の失敗による再送や二重タップで、同じ記録が2件できないようにするため。
- 旧 `garden_log` の「LINEユーザーID」「育成拠点」「詳細場所」「画像URL」「DriveフォルダURL」列は、新しいシートには持ち込まない。

### 12.5 記録と写真の関連付け・写真の保存先 【最新】【保留】

- 【最新】写真は「記録」タブの**写真ファイルID列**で記録と結びつける。現時点では1記録1枚。
- 【最新】写真は保存先フォルダの **`写真/<年>/`** に保存する。年は作業日の年とする。場所ごとのフォルダには分けない（場所名を変えたときに、フォルダとずれるのを避けるため）。
- 【最新】写真のファイル名は **`作業日_場所名_記録ID.jpg`**（例：`2026-09-27_北側花壇_3f9c2e1a-….jpg`）とする。
  - ファイル名は、Driveで開いたときに人が見て分かりやすくするためのもの。**記録との正式な結びつきは、記録IDと写真ファイルIDで行う**。
  - 場所名に含まれる `/`・`\`・制御文字は `_` に置き換える。
  - 写真には、Driveの非公開メタデータ（`appProperties`）として記録IDを付ける。同じ記録IDで再送されたときは、すでに保存した写真を使い、2枚目を作らない。
- 【最新】写真を見るときは、LIFFからDriveを直接開かず、サーバー（`GET /api/photos/:fileId`、12.12節）を通して取得する。Driveの外部公開URLは作らない。
- 【保留／将来】複数の画像に対応する方法（列を配列にする、写真用のタブを分ける、など）。

### 12.6 場所シート「場所」タブ 【最新】

| 列 | 見出し | 内容 |
| --- | --- | --- |
| A | 場所ID | サーバーが発行するID（`loc_` ＋英数字10桁）。「記録」タブの場所IDと結びつける |
| B | 場所名 | 利用者が付ける名前 |
| C | 登録日時 | 登録した日時（保存はISO形式、12.7節） |
| D | 更新日時 | 空欄の列として用意。名前の変更機能は未実装 |
| E | 削除日時 | 空欄の列として用意。削除（非表示）機能は未実装 |

- 場所名は**20文字まで**とする（絵文字も1文字と数える）。
- 場所名は保存前に**NFKC正規化**し、**前後の空白を除去**する（全角英数や半角カナなどの表記の揺れをそろえる）。
- **同じ名前の場所がすでにある場合は新規作成せず、既存の場所を返す**（削除済みの場所は比較の対象外）。
- 場所は名前だけで登録できる。写真・方角・詳細場所は持たない（10章）。
- 一覧は**登録順で固定表示**する（5.2節）。**最近使った順は採用しない。**
- 書き込みは `valueInputOption=RAW` で行い、見出し行が想定と違う場合は自動で直さずにエラーにする（12.4節と同じ方針）。

### 12.7 日付の形式 【最新】

- **保存形式と表示形式を分ける。**
- 保存：並べ替えや比較がしやすいISO形式（作業日 `2026-09-25`、記録日時 `2026-09-25T16:31:05+09:00`）。
- 表示：ユーザーの目に触れる日付は、すべて `2026/09/25` の形式に統一する。

### 12.8 旧データの扱い 【最新】

- 既存の `garden_log` と写真フォルダは、旧データとしてそのまま残す。
- コピーや一括移行はしない。
- 旧データは削除しない。詳細場所列など旧仕様の列も、既存データから削除しない。
- 過去の写真で必要なものは、新しい記録として必要に応じて登録し直す（12.9節）。
- 旧データは、GASのアルバム機能（読み取り）で引き続き閲覧できるようにする。旧アルバムの見せ方は【保留】。
- 【最新】リッチメニューの入口を新しい画面へ切り替えても（12.10節）、旧データとGASの旧アルバムは消さない。旧LIFF（`liff/index.html`）も削除せず、切り戻し用・旧データ閲覧用として残す。
- 【要確認】（13.1節 Q4）実利用を始めたあとに、旧データ（`garden_log`）を見たいときの開き方（旧LIFFのURLを残して開けるようにするか、リッチメニューからは外すか）。
- 【最新】実データのバックアップ：本人専用の段階では、保存先のスプレッドシートと写真はGoogle Drive上の開発者のファイルであり、Drive・Sheetsの版の履歴で守られる。自動バックアップの仕組みは作らない。必要になったら検討する【保留】。

### 12.9 写真の送信と、過去写真の登録 【最新】

- 【最新】記録画面を開いたときには写真を読み込まない。写真を選んだときだけ端末上でプレビューし、保存するときにだけアップロードする。
- 【最新】写真は、記録の内容と一緒に**1回の送信**で送る（JSONの中にbase64で入れる。12.12節）。
- 【最新】APIが受け付ける写真は**JPEGのみ・1枚3MBまで**（base64にする前の大きさ）。HEICなどを端末で選んだ場合は、**LIFF側でJPEGに変換してから**送る。API側ではHEICなどに対応しない。
- 【最新】元の画像はそのまま送らず、LIFF側で縮小・圧縮してから送る。アルバムで見るのに十分な画質は残す。
  - 【最新】長辺 **1600px** に縮小し、JPEG品質 **0.8** で保存する。それでも3MBを超える場合は、品質を **0.7**、さらに **0.6** まで下げて圧縮し直す。0.6でも超える場合は、別の写真を選ぶよう案内する。
  - 【最新】写真を選んだ時点で縮小・圧縮しておき、保存時の待ち時間を減らす。
  - 【最新】端末上で描き直してJPEGにするため、撮影位置などのEXIF情報は送らない（9章のプライバシーの考え方にも合う）。
- 【最新】過去の写真は、通常の記録と同じフォームで選ぶ（カメラ撮影とライブラリ・クラウドからの選択の両方に対応する）。作業日は手で変更して登録する。
- 【将来】撮影日時（EXIF）を読み取って作業日を提案する機能。

### 12.10 LINEからの入口（正式な入口）とLINEトークの記録導線 【最新】【一部要確認】

#### 12.10.1 LINEからLIFFを開く導線 【最新】（2026-10-04決定）

入口は基本的にLINEとする。

```

↓

↓
上部ナビで「アルバム / 記録する / 相談」を切り替えて使う（5.4節）
```

- リッチメニューを押してから場所タイルが出るまでの操作は、**1タップ**（LINEログインの同意画面は初回だけ）とする。
- 開いたときに選ばれている機能は「記録する」とする（5.4節）。URLに `?tab=album` / `?tab=record` が付いていれば、その機能を選んだ状態で開く（現行のリッチメニューの `?tab=` と同じ書き方。`?tab=consult` は「記録する」で開き、相談の準備中の案内を出す）。
- 画面の見た目と操作は、検証用ページ（5.4節・6.3節・8.2節）のまま変えない。

#### 12.10.2 正式な入口のページ 【最新】【要確認あり】

これまで画面の確認は、検証用ページ `liff/beta/index.html` を検証用LIFF（Keepメモに送ったURL）から開くか、PCのlocalhostで `?preview=件数` を付けて仮のデータで表示する方法で行ってきた。`?preview` は**localhostだけで働く開発用の仮表示**であり（本番のホストでは無効）、正式な入口には使わない。正式な入口は、本物のLIFF・本人確認・APIを通る次のページとする。

- **正式な入口のページを `liff/app/index.html` とする**（GitHub Pagesでは `/sodalog/app/`）。中身は検証用ページの画面と同じとし、違うのは使うLIFF IDなどの設定だけにする。
  - `?preview=件数` の仮表示は、正式な入口でも localhost に限って残してよい（開発用）。
  - 検証用ページ `liff/beta/` は、正式な入口に入れる前の変更を試す場所として残す。2つのページで画面のコードを二重に管理しないための方法（共通部分を1つのファイルにまとめる、など）は、実装時に決める。
  - `/home` は使わない（ホーム画面にあたるのは「記録する」の場所タイルであり、別の画面を増やさないため）。
- **【要確認】（13.1節 Q1）正式な入口をどのLIFFアプリで開くか**：
  | 案 | 内容 | 長所 | 短所 |
  | --- | --- | --- | --- |
  | (A) 本番LIFF（`2010871516-DJ2YSRIw`）で `/app/` を開く（推奨案） | リッチメニューのURLを `https://liff.line.me/2010871516-DJ2YSRIw/app/` のように変える（またはLINE Developersで本番LIFFのエンドポイントを `/sodalog/app/` に変える） | 「本番LIFF＝毎日使う入口」「検証用LIFF＝試す場所」の役割がはっきりする。旧画面 `liff/index.html` はファイルとして残せる | 本番LIFFのスコープ・設定を確認する必要がある。旧LIFFへの導線がリッチメニューからなくなる（12.8節） |
  | (B) 検証用LIFF（`2010871516-iHZTvGWU`）をリッチメニューから開く | リッチメニューのURLを検証用LIFFに向けるだけ | 変更が最も少ない | 「検証用」と「毎日使う入口」が同じになり、試しの変更がそのまま実利用に出てしまう |
  - どちらの案でも、Cloud Run側（本人確認・API・CORSの配信元）とGAS側は変えずに済む見込み（2つのLIFFは同じLINEログインチャネルに属し、配信元も同じGitHub Pages）。実機で確かめてから切り替える。

#### 12.11.1 目的と前提

- 利用者一人ひとりが自分のGoogleアカウントを連携し、**その人自身のGoogle Drive上に**、アプリがフォルダとスプレッドシートを作成して記録を保存する（12.3節の保存先を利用者ごとに持つ）。
- 利用者はLINEユーザーとして識別し（LIFFのIDトークンで確認）、それにGoogleアカウントを1つ結びつける。
- スコープは今と同じく `drive.file`・`openid`・`userinfo.email` だけとする。
- 現在の開発者1人用の構成（12.11.8節）は、この仕組みを作るための検証用であり、最終形ではない。

#### 12.11.2 全体の流れ（案）

```
[LINEアプリ内のLIFF]
 1. 利用者が「Googleと連携する」を押す
 2. LIFF → Cloud Run  POST /api/google/link-tickets
      （Authorization: LIFFのIDトークン。サーバーがLINEで検証し、LINEユーザーIDを特定）
 3. Cloud Run：1回限り・短時間有効の「連携チケット」を発行
      Firestoreには、チケットのハッシュ値とLINEユーザーIDと有効期限だけを保存
      LIFFへ「連携開始URL」を返す（https://…/oauth/start?ticket=…）
 4. LIFF：liff.openWindow({ url, external: true }) で端末の標準ブラウザを開く

[外部ブラウザ（Safari / Chrome など）]
 5. Cloud Run  GET /oauth/start?ticket=…
      チケットを検証して「使用済み」にする（1回限り）
      確認画面：「LINEアカウント（表示名）とGoogleアカウントを連携します」→［続ける］
 6. Cloud Run：state と PKCE を作り、Googleの同意画面へ移動
 7. 利用者がGoogleアカウントを選び、同意する（Drive の項目にチェック）
 8. Google → Cloud Run  GET /oauth/callback?code=…&state=…
      state を検証（1回限り）→ そこに結びついたLINEユーザーIDを取り出す
      認可コードをトークンに交換 → GoogleのIDトークンを検証
 9. Firestoreの users/{LINEユーザーID} に連携情報を保存（refresh tokenは暗号化。12.11.7節）
10. 利用者のDriveに保存先（フォルダ・スプレッドシート・「記録」「場所」タブ）を作成し、
      そのIDをFirestoreに記録（何度実行しても1組だけ。12.3節と同じ方式）
11. 完了画面：「連携しました（Google：a***@gmail.com）」「LINEに戻る」ボタン

[LINEアプリ内のLIFF]
12. 利用者がLINEに戻る → LIFFが GET /api/google/status で連携状態を再取得
      連携済みなら、場所の登録（10章）に進む
```

- 追加が想定されるルート：`POST /api/google/link-tickets`、`GET /api/google/status`、`POST /api/google/unlink`。既存の `/oauth/start`・`/oauth/callback` は、チケット方式に作り替える。
- いずれも新しいルート、または既存のOAuth検証用ルートの変更であり、LINE Webhook（`/webhook/line`）とGASの処理には触れない。

#### 12.11.3 外部ブラウザが必要な理由

- LIFFは、LINEアプリに組み込まれたブラウザ（WebView）の中で動く。
- Googleは、アプリに組み込まれたブラウザからのOAuthログインを**セキュリティ上の理由で拒否する**（`disallowed_useragent` エラー）。組み込みブラウザでは、アプリ側がパスワード入力を盗み見られる可能性を排除できないためである。
- そのため、Googleとの連携の部分だけは、`liff.openWindow({ external: true })` で**端末の標準ブラウザ**を開いて行う必要がある。
- 外部ブラウザにはLINEのログイン状態やLIFFのIDトークンが引き継がれない。そのため、「このブラウザで行う連携は、どのLINEユーザーのものか」を別の方法で安全に伝える必要がある（12.11.4節）。

#### 12.11.4 LINEユーザーとGoogleアカウントを安全に結びつける方法

**選択肢**

| 方式 | 内容 | 評価 |
| --- | --- | --- |
| (a) LIFFのIDトークンをURLに付けて外部ブラウザへ渡す | `…/oauth/start?id_token=…` | **採用しない**。IDトークンは有効期間中に何度でも使え、ブラウザの履歴・ログ・共有URLに残ると、なりすましに使われるおそれがある |
| (b) LINEユーザーIDをURLに付けて渡す | `…/oauth/start?line_user_id=…` | **採用しない**。誰でもURLを書き換えて、他人のLINEユーザーIDで連携できてしまう |
| (c) **1回限り・短時間有効の連携チケット**（推奨案） | LIFF側で本人確認を済ませたあとに、サーバーが推測できない乱数のチケットを発行し、外部ブラウザにはチケットだけを渡す | チケットだけでは何もできず、1回使うと無効になり、数分で期限が切れる |
| (d) 外部ブラウザでLINEログインをやり直す | 外部ブラウザでLINEログインしてからGoogleへ | 確実だが、利用者の操作が1段増え、外部ブラウザでのLINEログインに慣れていない人がつまずく |

**残るリスクと対策（チケット方式の場合）**

- **連携の乗っ取り（他人のチケットのURLを踏ませる攻撃）**：攻撃者が自分のLINEアカウントで発行したチケットのURLを利用者に送り、利用者がそれを開いて自分のGoogleアカウントで同意すると、**利用者のGoogleが攻撃者のLINEアカウントに結びついてしまう**。
  - 対策の候補：チケットの有効期限を短くする（例：5分）／Googleへ進む前に「どのLINEアカウント（表示名）と連携するか」を表示して確認させる／連携後、LIFF側に「連携中のGoogleアカウント（メールアドレスの一部）」を表示し、解除もできるようにする。
  - どこまで対策するか（確認画面を必須にするか、表示名をどこから取得するか）は未確定。
- **チケットのURLが外部ブラウザの履歴に残る**：1回使った時点で無効になり、有効期限も短いため、影響は限定的。応答に `Referrer-Policy: no-referrer` を付け、ログにチケットを出さない。

#### 12.11.5 チケットと `state` の役割

| | 連携チケット | OAuthの `state` |
| --- | --- | --- |
| 役割 | 「この外部ブラウザでの連携は、LIFFで本人確認したどのLINEユーザーのものか」を伝える | 「Googleから戻ってきた応答が、このサーバーが開始した連携に対するものか」を確かめる（CSRF対策）。LINEユーザーIDとPKCEの値に結びつける |
| 発行するタイミング | LIFFで「連携する」を押したとき（手順2〜3） | `/oauth/start` でチケットを使ったとき（手順6） |
| 有効期限の案 | 5分 | 10分 |
| 使える回数 | 1回（使った時点で無効） | 1回（callbackで使った時点で無効） |
| 保存方法の案 | Firestoreに**ハッシュ値のみ**保存。チケット自体は保存しない | Firestoreにハッシュ値・LINEユーザーID・PKCEの検証値を保存。あわせて、同じブラウザから戻ってきたことを確かめるため、HttpOnlyのクッキーにも結びつける |
| 片付け | FirestoreのTTL（有効期限による自動削除）で消す | 同左 |

- 今のSTEP 3の実装では、`state` とPKCEの値をクッキーだけで持ち、保存先を1人に固定している。利用者ごとの連携では、`state` に「どのLINEユーザーか」を結びつける必要があるため、サーバー側（Firestore）にも記録を持つ形に変える。

#### 12.11.6 Firestoreに保存する情報／保存しない情報（案）

**保存する情報**

| コレクション | 項目 | 用途 |
| --- | --- | --- |
| `users/{LINEユーザーID}` | GoogleのユーザーID（`sub`） | 連携先の特定。別のGoogleアカウントに付け替えたかどうかの判定 |
| | Googleのメールアドレス | 「連携中：a***@gmail.com」と表示するため（全部保存するか、一部を伏せて保存するかは未確定） |
| | **暗号化したrefresh token**、暗号鍵のバージョン | 利用者のDriveやSheetsにアクセスするため（12.11.7節） |
| | 許可されたスコープ | `drive.file` が外されていないかの確認 |
| | 保存先：フォルダID・スプレッドシートID・スキーマのバージョン | 毎回Driveを検索しないで済むようにするため（`appProperties` での検索は復旧用として残す） |
| | 連携状態（連携済み／再連携が必要／解除済み）、連携日時、更新日時 | 画面表示と再連携の案内 |
| `linkTickets/{チケットのハッシュ値}` | LINEユーザーID、有効期限、使用済みかどうか | 12.11.5節 |
| `oauthStates/{stateのハッシュ値}` | LINEユーザーID、PKCEの検証値、有効期限 | 12.11.5節 |

**保存しない情報**

- アクセストークン（有効期限1時間。サーバーのメモリ上でだけ使う）
- LIFFやGoogleのIDトークン、認可コード（その場で検証して捨てる）
- チケットや `state` そのもの（ハッシュ値だけを保存する）
- **記録の中身（場所名・作業・メモ・写真など）**。これらは利用者自身のSheetsとDriveにだけ保存し、アプリ側には持たない
- LINEの表示名やプロフィール画像（必要なときにその場で取得する）
- パスワード類（そもそも受け取らない）

#### 12.11.7 refresh tokenの保存方法（選択肢）

refresh tokenがあれば、その利用者のDriveにある「アプリが作ったファイル」を読み書きできる。そのため、漏えい時の影響が最も大きい情報として扱う。

| 方式 | メリット | デメリット |
| --- | --- | --- |
| (A) Firestoreに暗号化せず保存（Google側の保存時暗号化とIAMに任せる） | 実装が最も簡単 | Firestoreを読める権限があれば、そのままトークンを取り出せる。**今の実行アカウントはプロジェクト全体の「編集者」権限を持っているため**、影響範囲が広い。データのエクスポートやバックアップからも漏れうる |
| (B) Firestoreにアプリ側で暗号化して保存（AES-256-GCM）。暗号鍵はSecret Managerに置く | データベースだけが漏れても、トークンは使えない。追加費用がほぼない | 鍵の管理（ローテーション、旧鍵での復号）を自分で実装する必要がある。アプリ自体が侵害されると、鍵とデータの両方に届く |
| (C) FirestoreにCloud KMSで暗号化して保存（エンベロープ暗号化） | 鍵がKMSの外に出ない。復号の操作がすべて監査ログに残る。鍵のローテーションをGoogleが管理し、「復号できる権限」を実行アカウントだけに絞れる | 設定の手間が増える。KMSの費用がかかる（鍵1つあたり月数十円程度＋操作回数に応じた課金。個人〜小規模なら少額の見込み）。復号のたびに通信が発生するため、短時間のキャッシュが必要 |
| (D) 利用者ごとにSecret Managerのシークレットを作る | 利用者ごとに権限を分けられる | シークレットの数が利用者数に比例して増え、費用・上限・権限の管理が煩雑になる。利用者ごとのデータを入れる用途には向かない |

- **推奨案（未確定）**：一般公開を前提とするなら (C)、限定したテスト運用の間は (B) でも可。どちらを選ぶ場合も、暗号化・復号の処理を1か所にまとめ、あとから (B) から (C) へ切り替えられる形にする。
- **どの方式を選んでも必要なこと**：Cloud Runを**専用の最小権限サービスアカウント**に切り替える（今の既定のアカウントはプロジェクト全体の編集者権限を持つ。この切り替えはすでに別STEPで予定している）。
- 連携を解除したときは、Googleのトークン取り消しAPIでrefresh tokenを無効にしてから、Firestoreのデータを消す。利用者のDriveにある記録やファイルは、利用者自身のものなので削除しない。

| `GET /api/locations` | 削除されていない場所を**登録順で固定**して返す（5.2節・12.6節）。画像の情報は含まない。`?include=counts` を付けたときだけ、各場所の総記録数 `recordCount` を付ける（下記） | 200 `{ locations: [{ id, name, createdAt }] }`（`include=counts` のときは各場所に `recordCount` が加わる） |
| `POST /api/locations` | 本文 `{ name }` で場所を登録する。場所名は12.6節のルールで正規化・確認する | 新規作成は201、同じ名前がすでにあれば既存の場所を返して200（どちらも `{ location, created }`）。場所名が不正なら400 `invalid_name` |
| `POST /api/records` | 記録を保存する（写真1枚を含められる）。入力は下の表のとおり | 新規保存は201、同じ記録IDがすでにあれば何も書かずに既存の記録を返して200（どちらも `{ record, created }`） |

**`POST /api/records` の入力**

| 項目 | 必須 | 内容 |
| --- | --- | --- |
| `recordId` | 必須 | LIFFが作る記録ID（`crypto.randomUUID()` の形式、12.4節） |
| `workDate` | 必須 | 作業日 `YYYY-MM-DD`。実在する日付で、日本時間の今日以前（6.1節） |
| `locationId` | 必須 | 「場所」タブの場所ID。削除されていない場所であること |
| `plantTags` | 任意 | 文字列の配列。1つ20文字まで・最大10個（3.1節） |
| `workTypes` | 任意 | 9項目のどれかの配列（6.2節）。重複は除き、決まった順（6.2節）に並べ替えて保存する |
| `memo` | 任意 | 300文字まで（6章） |
| `photo` | 任意 | `{ mimeType: "image/jpeg", data: <base64> }`。JPEGのみ・3MBまで（12.9節） |

- 記録の成立条件（場所＋写真・作業内容・植物タグ・メモのどれか1つ以上、6章）を満たさない場合は400 `empty_record`。
- 場所名・記録日時・記録元は、LIFFから送られた値を使わずサーバーが決める（12.4節）。
- 処理の順番：記録IDの重複確認 → 場所の確認 → 写真の保存（12.5節） → 「記録」タブへの追記。写真の保存後に追記だけ失敗した場合は、同じ記録IDで再送すれば、保存済みの写真を使って保存を完了できる。
- エラーの応答：項目が不正なら400 `invalid_record`（どの項目か・理由を付ける）、場所が見つからなければ400 `unknown_location`、写真がJPEGでない・壊れているなら400 `invalid_photo`、写真が3MBを超えるなら413 `photo_too_large`。

**`GET /api/locations?include=counts`**（アルバム側の場所タイルの件数。5.4節）

- 場所一覧に加えて「記録」タブを読み、各場所に `recordCount`（その場所の総記録数。写真あり＋写真なし）を付けて返す。記録がない場所は `0`。
- 数える対象は `GET /api/album` の `total` と同じ（削除日時が入った行・記録IDがない行・作業日の形が不正な行は数えない）。サーバーの中でも同じ処理で絞り込み、件数が食い違わないようにしている。
- `include=counts` を付けないときの応答と処理は、付ける前と同じ（「記録」タブは読まない）。

**`GET /api/album?locationId=<場所ID>&year=<西暦>`**（アルバム。8.1節）

- `year` は省略できる。省略すると、その場所で記録がある最新の年になる。
- 返す内容：場所（ID・名前）、`total`（その場所の全年の件数）、`years`（作業日の年と件数の一覧、古い順）、`year`（今回返した年。記録が0件なら `null`）、`photoRecords`（写真あり。古い順）、`textRecords`（写真なし。新しい順）、`truncated`（写真あり・写真なしそれぞれ、上限の300件を超えて古い記録を省いたか）。
- 各記録は、記録ID・作業日・記録日時・作業内容・植物タグ・メモ・写真ファイルIDを返す。
- 削除日時（12.4節 L列）が入った行は対象にしない。
- エラーの応答：場所IDや年の形が不正なら400（`invalid_location_id` / `invalid_year`）、場所が見つからなければ404（`unknown_location`）。

**`GET /api/photos/:fileId?size=thumb|full`**（写真の中身。12.5節）

- サーバーが写真を中継して画像として返す。Driveの共有設定は変えない。
- 返す前に、Driveの非公開メタデータで**そだログがこの保存先に保存した写真か**を確かめる。そうでないファイル・ごみ箱に入ったファイルは404（`photo_not_found`）。
- `size=thumb`（省略時）：Driveが作るサムネイル（長辺480px）。取得できない場合や、まだ作られていない場合は、保存した画像をそのまま返す。
- `size=full`：保存した画像（長辺1600px。12.9節）をそのまま返す。
- 応答ヘッダー：
  - `Cache-Control: private, max-age=86400`：利用者の端末にだけ1日保存させる。同じファイルIDの写真は変わらないため。
  - `X-Sodalog-Photo-Source`：`thumbnail`（サムネイルを返した）か `original`（保存した画像を返した）。LIFFからも読めるようにしている。
- LIFFは、IDトークン（12.2節）を付けてこのAPIを呼び、受け取った画像を表示する。

**LIFF向けAPIの共通事項**

- 本人確認は12.2節・12.2.1節のとおり。IDトークンがない・不正なら401、許可していないユーザーなら403、LINE側に確認できないときは502を返す。
- CORSは、GitHub Pages上のLIFFの配信元だけを許可する。
- リクエスト本文のJSONの上限は、写真を送る `POST /api/records` だけ**5MB**（3MBの写真をbase64にすると約4MBになるため）、ほかのAPIは8KBとする。JSONの解析は `/api` 配下だけで行い、LINE Webhookの署名検証（生の本文が必要）には影響させない。
- 保存先は環境変数 `STORAGE_ENV` で選ぶ。本番用の保存先を作るまでは `test` だけを受け付ける（12.3節）。API用の設定やGoogle連携がなければ、`/api` 配下は503を返すだけで、Webhookなど他の機能は止めない。
- 保存先のタブの見出しが想定と違うときは、自動で直さず409を返す（12.4節・12.6節）。

**管理用**

| API | 内容 |
| --- | --- |
| `POST /admin/storage/setup?env=test` | 新しい保存先（フォルダ・スプレッドシート・「記録」タブ・「場所」タブ・「写真」フォルダ）を作成する。2回目以降は既存のものをそのまま使う（作り直さない）。`env=production` は正式に切り替えるまで拒否する（400） |
| `GET /admin/gas/ping` | Cloud Run → GAS の同期呼び出し（12.13節）の確認用。GASの `ping` を呼び、`{"ok":true,"action":"ping","elapsedMs":…}` を返す。GASの設定（`GAS_WEBHOOK_URL`・`GAS_SHARED_SECRET`）がなければ503、GASの呼び出しに失敗したら502 |

- 管理用APIは管理用トークン（`X-Admin-Token` ヘッダー）がなければ使えない（401）。LIFFからは呼ばない。

### 12.13 個人利用版の構成（2026-10-02決定） 【最新】

EDD2026への応募が終わり、一般公開・複数ユーザー対応を当面優先しないことにした。最優先は「今のそだログのUI・見た目を保ちながら、開発者本人が日常的に安定して使えること」とする。

**Gitの分岐**

| 名前 | 内容 |
| --- | --- |
| `main` | 公開を見据えた構成のまま止めておく（STEP 4-4b完了時点、コミット `4d1f194`） |
| タグ `checkpoint/public-ready-2026-10-02` | 上の時点の目印。GitHubにもpush済み。公開版を再開するときはここから見る |
| `personal-use` | 個人利用版の開発ブランチ。STEP 4-5以降はここで開発する（GitHubにpush済み） |

**基本構成**

```
LIFF → Cloud Run（LIFF IDトークンで本人確認）→ GAS（共有シークレット検証）→ 新しいスプレッドシート・Driveフォルダ
```

- Google Drive・Sheetsへの読み書きはGASが行う。Cloud RunはGoogleのAPIを直接呼ばない。これにより、OAuthのrefresh tokenの7日失効（12.2節）が日常利用の経路に関係しなくなる。
- LINE Webhook（LINE → Cloud Runで署名検証 → GASへ転送）は、これまでどおり維持する。
- 追加の費用はかけない。独自ドメインは取得しない。

**OAuth関連（保留）**

- Google Auth Platform は「テスト中」のままにする。本番公開（In Production）、独自ドメイン、公開要件（ホームページ・プライバシーポリシー・利用規約）への対応は保留する。
- STEP 3 で作ったOAuthの検証コード（`/oauth/*`）、Secret Managerの設定、`drive.file` のテスト用保存先（12.3節）は削除せず、将来再開できる状態で残す。日常利用の経路からは使わない。

**保存先**

- 旧 `garden_log` と旧写真フォルダは、旧データとしてそのまま残す（変更しない）。
- 新そだログは、GASが作る**新しいスプレッドシート・Driveフォルダ**を使い、新しいデータ構造でゼロから始める（STEP 4-6で作成）。旧データは移さない。

**写真**

- 写真はDrive上で**非公開のまま**にする。「リンクを知っている全員」への共有は使わない（庭や自宅が写るため）。
- 取得経路：LIFF → Cloud Run（本人確認）→ GAS（DriveAppで非公開の画像を読み、base64で返す）→ Cloud Run（バイナリに戻して返す）→ LIFF。
- まずはフルサイズだけを保存する（C案）。サムネイル専用のファイルは作らない。実機でアルバムが遅いと感じた場合だけ、2サイズ保存（サムネイル480px＋本体1600px、A案）への移行を検討する。
- Cloud Runの画像の応答には `Cache-Control: private, max-age=86400` を付ける。写真の差し替え・修正を将来実装する可能性があるため、`immutable` は付けない。

**Cloud Run → GAS の同期呼び出し（STEP 4-5）**

- Cloud Runの `callGasSync(action, payload, config)`（`server/src/gas.ts`）が、GASの `doPost` に `{sharedSecret, action, payload}` をPOSTし、応答のJSONを待つ。時間切れは25秒。
- 送り先と共有シークレットは、LINE Webhookの転送と同じ環境変数 `GAS_WEBHOOK_URL`・`GAS_SHARED_SECRET` を使う（新しい環境変数は増やさない）。
- GASの `doPost` は、共有シークレットを確かめたあと、本文に `action` があるときだけ `handleCloudRunAction()` で処理して `{ok:true, …}` または `{ok:false, error}` を返す。LINE Webhookの転送は `action` を持たないため、これまでの `events` の処理に進む。
- Cloud Runは、応答が `ok:true` でなければ失敗として扱う（共有シークレットが合わないとき、GASは `{status:"ok"}` だけを返すため、これも失敗になる）。
- 現在の action は `ping` だけ。保存・取得などの action は STEP 4-6 以降で追加する。

**LINEトークの旧記録機能**

- 新しいLIFFの開発・検証中は残す。
- 新しいLIFFを正式に使い始めた時点で、番号選択による記録と写真の後付け記録を終了する予定。
- 「使い方」などのボットの返信は当面残す。

- 場所の同名チェックと、記録IDの重複チェックは、Cloud Runの同じインスタンス内では同時保存を防いでいるが、複数のインスタンスにまたがる同時保存までは防げない。利用者が1人の現段階では問題にならないと判断している。複数ユーザーに対応するときに見直す。

**4-3bのUXで考えること**

- 実環境確認では、写真付きの初回保存に**約4.3秒**かかった（年フォルダの作成と写真のアップロードを含む。写真なしは約0.7秒）。「記録する」は速度を優先する（6章）ため、保存中の表示、待ち時間の感じ方、保存に失敗したときに同じ記録IDで再送できるようにすることを、4-3bで検討する。
  - 対応（4-3b）：写真は選んだ時点で縮小・圧縮しておく。保存中はボタンを押せなくして「保存しています…」と表示する。失敗したら同じ記録IDで「もう一度保存」できる（6.3節）。
  - iPhone実機での確認（2026-09-27）では、写真あり・なしとも保存の流れに問題はなかった（16.1節）。

**4-4bで考えること（4-4aの実測から）**

- 写真の読み込みには、サムネイルで約0.8秒、元画像で約1.8秒かかった。一覧では、見えてきた写真から順に読み込み、届くまでは淡い場所色の枠を表示する案を検討する。詳細では、先にサムネイルを表示し、元画像が届いたら差し替える案を検討する。
  - 対応（4-4b）：一覧は見えてきた写真から同時に4枚まで読み込み、届くまでは淡い場所色の枠を表示する。詳細は先にサムネイルを表示し、元画像が届いたら差し替える（8.2節）。
- 写真には縦長と横長がある。一覧の写真枠をどちらでも見やすい形にする。
  - 対応（4-4b）：一覧は正方形のタイルに写真の中央を切り抜いて表示する。詳細では写真全体を表示する（8.2節）。

**アルバム画面について残っている未検証事項**

- 1年に写真ありまたは写真なしの記録が300件を超える場合の表示（8.2節）は、実データではまだ確かめていない。
- 写真が多い年の読み込みの速さ・通信量は、実際の庭での利用（STEP 4-11）で確かめる。
- 上部ナビとアルバム画面の実機確認はiPhoneだけで行った。Androidと、横幅320px級の端末の実機ではまだ確かめていない（320pxはPCのプレビューでだけ確認）。

**記録画面について残っている未検証事項**

- iPhone以外（Android）のLINE内ブラウザでの動作は、まだ確かめていない。
- 画面の小さい端末（iPhone SE 第1世代など、横幅320px級）では、作業日のカレンダーがシートの中でスクロールする想定（PCのプレビューで確認）。実機ではまだ確かめていない。
- 記録画面を長い時間開いたままにしてから保存したとき、LIFFのIDトークンの有効期限が切れて401になるか。なる場合は「LINEの認証が切れました」と表示され、入力した内容は失われる。自動でログインし直すなどの改善が必要かは、実機で確かめてから決める。
  - 参考：PCのブラウザで検証用ページを開くと、期限切れのIDトークンがブラウザに残り、再読み込みしても401になることがある（2026-09-27に発生）。`liff.logout()` のあとにログインし直すと解消する。
