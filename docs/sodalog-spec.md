## 1. 設計原則 【最新】

1. 記録するために育てるのではなく、育てることを助けるために記録する。
2. 場所を記録の主語とする。
3. 植物は必要なときだけタグとして記録する。
4. 人間に入力させなくていい情報は、できるだけ入力させない。
5. 「記録する」は速度を優先する。
6. 「アルバム」は振り返りや写真表示を優先する。
7. 写真共有を前提としない。
8. 将来機能のために、現在の記録体験を複雑にしない。

## 2. 基本コンセプト 【最新】

そだログは、「記録するために育てるのではなく、育てることを助けるために記録する」ことを基本思想とする。

- 園芸作業中に細かな入力を要求せず、できるだけ短い操作で記録を残せることを優先する。
- 「人間に入力させなくていい情報は、できるだけ人間に入力させない」ことを設計原則とする。
- 入口はLINE。LINE公式アカウントのリッチメニューからLIFFを開き、「記録する」「アルバム」「相談」の3タブで使う。「相談」は準備中の表示にとどめる。

### 2.1 開発ライン 【最新】

そだログの開発は、次の2つのラインに分けて扱う。**主目的は (1) であり、(2) は (1) の成果を他の利用者にも安全に届けるための土台である。**

| ライン | 位置づけ | 主な内容 |
| --- | --- | --- |
| **(1) 記録体験の改善**（主目的） | そだログの中心課題である「園芸中の記録負担を減らすこと」に取り組む。継続して改善する | 場所中心の記録（3章）／場所タイルからのすばやい選択（5章）／1画面での記録（6章）／場所以外は任意入力（6章）／作業チップ（6.2節）／植物のタグ化（3章）／場所の自由登録（10章・12.6節）／実際に庭で使った結果にもとづく記録導線の改善 |
| (2) マルチユーザー化・認証基盤 | (1) で改善した記録体験を、開発者以外の利用者にも安全に提供するための基盤。記録機能そのものを完成させる工程ではない | Google OAuth、利用者ごとの保存先（12.3節）、LINEユーザーとGoogleアカウントの結びつけ（12.11節）、秘密情報の管理、専用サービスアカウント |

- (2) の作業は、(1) の記録体験を複雑にしたり遅くしたりしない範囲で進める（設計原則8）。
- (2) の進み具合で、(1) の改善を止めない。(1) は開発者1人用の構成の上でも検証と改善を続けられる。

## 3. 記録単位 【最新】【過去から変更】

記録の主語は「植物」ではなく「場所」とする。

場所の例：北側花壇／南側花壇／玄関／ベランダ／室内

植物は場所に付随する任意の「タグ」として扱う。

```
場所：北側花壇
作業：剪定
植物タグ：アジサイ、ホスタ
```

- 植物の選択は必須にしない。
- 植物タグを付けない記録は「その場所全体に対する記録」とみなす。
- 「全体」という専用の植物タグは作らない。
- 1件の記録に植物タグを0〜複数付けられる。

**過去から変更**：旧仕様では「1件の記録＝1つの場所＋1つの植物」を前提にしており、植物名の入力欄は1つだけだった。デモデータには「全体」という仮の植物名が使われていた。

### 3.1 植物タグの保存形式 【最新】

- JSON配列の文字列で保存する（例：`["アジサイ","ホスタ"]`）。
- タグなしは `[]` とする。
- 区切り文字方式（「、」「,」など）は、値そのものに記号が含まれると壊れるため採用しない。

### 3.2 植物タグの入力UI 【保留】

自由入力、候補表示、よく使うタグの表示、タグのID管理は未確定。記録フォームを実装するSTEPの直前に決める。

## 4. 詳細場所 【最新】【過去から変更】

「北側花壇 ＞ 東側」「北側花壇 ＞ 中央」のような、場所の下位にある「詳細場所」は廃止する方向とする。

理由：

- 入力項目を増やさないため
- Driveやデータ構造を必要以上に複雑にしないため
- 園芸記録を続けやすくするため

細かく分けたい場合は、場所名そのものを分けて登録する（例：「北側花壇・東」）。

- 新しい記録シート（12章）には詳細場所の列を設けない。
- **既存の `garden_log` の詳細場所列と、そのデータは削除しない**（12.8節）。

**過去から変更**：旧仕様では「場所（庭／室内／その他）×詳細場所（北側／南側／中央／東側／西側）」の固定2段選択だった。写真のDriveフォルダも「場所/詳細場所/年」の階層だった。

## 5. 場所選択UI 【最新】【過去から変更】

### 5.1 場所名のコラージュ風タイル 【最新】

「記録する」の場所選択画面は、**場所名だけをタイル状に配置したコラージュ風UI**とする。これは保留事項ではなく、現時点の採用方針である。

「写真を並べたコラージュ」ではなく、「場所名をタイル状に配置したコラージュ風UI」を意味する。

```
┌──────────────┐
│   北側花壇    │
├──────┬───────┤
│南側花壇│ 玄関 │
├──────┴───────┤
│     室内      │
└──────────────┘
```

- 場所選択画面では画像を読み込まない。画像を非表示にするだけでなく、この画面のための画像取得処理そのものを行わない。
- 場所タイルをタップすると、その場所を選択した状態で記録画面へ進む。
- 場所名が読みやすく、タップしやすいことを優先する。
- タイルのサイズ・色・配置の細部は、実装STEP（STEP 4-2）の直前に決める。

### 5.2 場所タイルの並び順 【最新】

- **登録順で固定表示する**（先に登録した場所が先頭、新しく登録した場所は末尾に追加）。
- 「最近使った順」は場所の並びには採用しない。

理由：ユーザーが場所タイルを「画面上の位置」で覚えて選べることを優先するため。使うたびに位置が変わると、かえって選びにくくなる可能性がある。

**過去から変更**：旧仕様（STEP 8）では、「最近使った場所」を3〜5件、代表写真付きのカードで並べる方針だった。これは本番で実装・稼働している（16章）。新方針では「最近使った場所」を場所選択の仕組みとしては採用しない。

## 6. 記録画面 【最新】

- 「記録する」は速度を最優先する。
- 場所を選択したあとは、できるだけ1画面で記録を完了できるようにする。
- 場所は必須、それ以外は原則任意とする。任意項目の候補は、作業内容・植物タグ・写真・メモ。
- **記録の成立条件**：場所＋（写真・作業内容・植物タグ・メモのどれか1つ以上）。場所だけの空の記録は保存しない。
- 詳細場所の入力は求めない（4章）。
- 場所の代表写真は持たない（7章）。
- 記録画面では、場所の写真も過去の記録写真も読み込まない。
  - 今回の記録に添付する写真の選択・プレビュー・保存は記録機能に含む。
- 園芸作業中でも迷わず入力できることを優先する。

### 6.1 作業日 【最新】

- 作業日の入力欄は維持し、初期値は今日とする。手で変更できる。
- 過去の写真を登録するときは、作業日を手で直す（12.9節）。
- 撮影日時（EXIF）から作業日を提案する機能は必須にしない【将来】。

### 6.2 作業内容 【最新】【保留】

- 【最新】作業内容は任意で、複数選択できる。JSON配列で保存し、未選択は `[]`。
- 【最新】現在の本番では、作業チップは**場所ごとの使用頻度順**に並ぶ（STEP 10で実装済み）。
- 【保留】今後もこの並び順を正式に採用し続けるかどうかは未確定。

---

## 7. 写真の扱い 【最新】【過去から変更】

- 場所ごとの「代表写真」は持たない。
  - 理由：場所選択画面で写真を読み込むと、その待ち時間で記録の開始が遅れ、ユーザーが記録そのものをやめてしまうおそれがあるため。
- 「記録する」と「アルバム」とで、UXの優先順位を分ける。
  - 記録する＝速度優先
  - アルバム＝写真による振り返り優先
- 日々の記録には、必要に応じて写真を添付する。
- 当面は**1記録1枚**とする。複数画像への対応は【保留／将来】とする（13章・14章）。

**過去から変更**：旧仕様（STEP 8）では場所エンティティに `representativeImage`（その場所の最新の記録写真）を持たせ、場所カードに表示していた。写真は、記録を保存したあとにLINEのトークで送って紐付ける方式だった。

---

## 8. アルバム 【最新】

- 日々の記録写真を見て振り返る機能とする。
- 写真表示が主な目的なので、一定の画像読み込み時間は許容する。
- 記録画面では画像を読み込まず、アルバム画面では画像を使う、という役割分担とする。
- 場所写真の廃止を理由に、記録写真の取得やアルバム表示を削除しない。
- アルバムの最終UI（構造・並び順・絞り込み・ページ分割）は【保留】。

---

## 9. SNS・写真共有 【最新】

- そだログはSNS型の園芸コミュニティを目指さない。
- 庭・ベランダ・住宅周辺の写真には、住宅外観・窓・周辺環境・生活環境などが写り込むおそれがある。そのためプライバシーの観点から、写真共有を前提としたサービス設計にはしない。
- 写真は原則として、本人が自分の園芸環境や変化を振り返るためのものとして扱う。
- 写真は保存先のDriveで非公開のまま扱い、共有設定は変更しない。

## 10. 初回オンボーディング 【最新（理想導線）】

```
LINE公式アカウントを友だち追加
↓
Googleアカウント連携
↓
植物を育てている場所を登録
↓
場所タイル一覧
↓
場所を選択
↓
最初の記録
```

最初の場所登録では、入力を最小限にする。

| 項目 | 扱い |
| --- | --- |
| 場所名 | 必須 |
| 写真 | 不要 |
| 方角 | 不要 |
| 詳細場所 | 不要 |

- 最初の場所を登録したら、そのままその場所での記録に進めることを目指す。
- Google連携を拒否・失敗・解除したときの動作と、複数ユーザー向けの連携導線は【保留】（12.2節）。

**過去から変更**：旧仕様では、場所の自由登録を「Phase B（STEP 13）」として後回しにし、代表写真付きで登録する想定だった。新しい保存先（12章）は空の状態から始まるため、場所名だけで登録できる機能を、新しい記録機能の前提として前倒しする。

## 12. 技術方針（2026-09-25決定） 【最新】

### 12.1 全体構成

| 経路 | 構成 |
| --- | --- |
| 現行（本番稼働中） | LINE → Cloud Run（LINE署名検証）→ GAS（共有シークレット検証）→ `garden_log` シート・写真フォルダ（開発者のDrive） |
| 現行のLIFF | GitHub Pages（`liff/index.html`）→ `liff.sendMessages` でLINEへテキスト送信 → 上の経路で保存。アルバムはLIFFからGASの `action=list` / `action=image` を直接呼ぶ |
| 新方式（開発中） | LIFF → Cloud Run のAPI → Google Drive API / Google Sheets API → **利用者本人のGoogle Drive上に、アプリが作成したフォルダ・シート** |

- 写真付きの記録保存は、Cloud Runに新しいAPIを作って行う（B案）。GASにLIFF用のアップロード処理は追加しない。
- 最終的な構成（一般公開・複数ユーザー）は、Cloud Run（Node.js/TypeScript）＋ Google OAuth ＋ 利用者本人のDrive/Sheets とする。開発者のDriveに一般利用者の記録・写真を集めない。

### 12.2 認証

- **LINEユーザーの確認**：LIFFのIDトークンをサーバー側で検証してユーザーを特定する。クライアントから送られてきたユーザーIDは信用しない。
- **Google**：OAuthのスコープは `drive.file`・`openid`・`userinfo.email` の3つのみ。高機密スコープや制限付きスコープは使わない。
- **refresh token**：開発段階（利用者は開発者1人）ではSecret Managerに保存する。複数ユーザーに対応するときはユーザーごとに管理する（Firestoreを予定）【保留】。
- OAuthの公開ステータスが「テスト中」のときのrefresh tokenの有効期限は、別途観測中。結果に応じて、正式な切り替えの前に対処方法を決める。

### 12.3 保存先

- **正式な保存先は、アプリが `drive.file` で新しく作成するフォルダとスプレッドシート**とする。
- `drive.file` では、アプリが作っていない既存の `garden_log` と写真フォルダにはアクセスできない（2026-09-25に実測。404 notFound）。一方、アプリが作ったファイルへの作成・追記・読み取りはできる（同日に実測）。
- 作成したファイルは、Driveの非公開メタデータ（`appProperties`）で見分ける。
- **検証中はテスト用の保存先を使う**（フォルダ「そだログ（テスト）」、スプレッドシート「そだログ記録（テスト）」）。本番用の保存先は、正式に切り替えるときに作成する。

### 12.4 記録シート「記録」タブ 【最新】

| 列 | 見出し | 内容 |
| --- | --- | --- |
| A | 記録ID | 保存時にLIFFが作る一意のID。重複保存の防止に使う |
| B | 記録日時 | サーバーが保存した日時 |
| C | 作業日 | 作業した日（手で変更できる） |
| D | 場所ID | 「場所」タブのID |
| E | 場所名 | 記録した時点の場所名 |
| F | 植物タグ | JSON配列。タグなしは `[]` |
| G | 作業内容 | JSON配列。未選択は `[]` |
| H | メモ | 自由記述 |
| I | 写真ファイルID | DriveのファイルID。写真がなければ空欄。1記録1枚 |
| J | 記録元 | 当面は `liff` |
| K | 更新日時 | 空欄の列として用意。修正機能は未実装 |
| L | 削除日時 | 空欄の列として用意。取り消し（論理削除）機能は未実装 |

- 書き込みは `valueInputOption=RAW` で行い、入力値が数式として実行されたり、日付型へ自動変換されたりしないようにする。
- 見出し行が想定と違う場合は、自動で直さずにエラーにする（手作業の編集で列がずれたときにデータを守るため）。
- 旧 `garden_log` の「LINEユーザーID」「育成拠点」「詳細場所」「画像URL」「DriveフォルダURL」列は、新しいシートには持ち込まない。

### 12.5 記録と写真の関連付け 【最新】【保留】

- 【最新】写真は「記録」タブの**写真ファイルID列**で記録と結びつける。現時点では1記録1枚。
- 【保留／将来】複数の画像に対応する方法（列を配列にする、写真用のタブを分ける、など）。

### 12.6 場所シート「場所」タブ 【最新】

| 列 | 見出し | 内容 |
| --- | --- | --- |
| A | 場所ID | サーバーが発行するID（`loc_` ＋英数字10桁）。「記録」タブの場所IDと結びつける |
| B | 場所名 | 利用者が付ける名前 |
| C | 登録日時 | 登録した日時（保存はISO形式、12.7節） |
| D | 更新日時 | 空欄の列として用意。名前の変更機能は未実装 |
| E | 削除日時 | 空欄の列として用意。削除（非表示）機能は未実装 |

- 場所名は**20文字まで**とする（絵文字も1文字と数える）。
- 場所名は保存前に**NFKC正規化**し、**前後の空白を除去**する（全角英数や半角カナなどの表記の揺れをそろえる）。
- **同じ名前の場所がすでにある場合は新規作成せず、既存の場所を返す**（削除済みの場所は比較の対象外）。
- 場所は名前だけで登録できる。写真・方角・詳細場所は持たない（10章）。
- 一覧は**登録順で固定表示**する（5.2節）。**最近使った順は採用しない。**
- 書き込みは `valueInputOption=RAW` で行い、見出し行が想定と違う場合は自動で直さずにエラーにする（12.4節と同じ方針）。

### 12.7 日付の形式 【最新】

- **保存形式と表示形式を分ける。**
- 保存：並べ替えや比較がしやすいISO形式（作業日 `2026-09-25`、記録日時 `2026-09-25T16:31:05+09:00`）。
- 表示：ユーザーの目に触れる日付は、すべて `2026/09/25` の形式に統一する。

### 12.8 旧データの扱い 【最新】

- 既存の `garden_log` と写真フォルダは、旧データとしてそのまま残す。
- コピーや一括移行はしない。
- 旧データは削除しない。詳細場所列など旧仕様の列も、既存データから削除しない。
- 過去の写真で必要なものは、新しい記録として必要に応じて登録し直す（12.9節）。
- 旧データは、GASのアルバム機能（読み取り）で引き続き閲覧できるようにする。旧アルバムの見せ方は【保留】。

### 12.9 写真の送信と、過去写真の登録 【最新】【保留】

- 【最新】記録画面を開いたときには写真を読み込まない。写真を選んだときだけ端末上でプレビューし、保存するときにだけアップロードする。
- 【最新】元の画像はそのまま送らず、LIFF側で縮小・圧縮してから送る。アルバムで見るのに十分な画質は残す。
  - 【保留】具体的な値（案：長辺1600px、JPEG品質0.8程度）は写真保存APIを実装する直前に決める。
- 【最新】過去の写真は、通常の記録と同じフォームで選ぶ（カメラ撮影とライブラリ・クラウドからの選択の両方に対応する）。作業日は手で変更して登録する。
- 【将来】撮影日時（EXIF）を読み取って作業日を提案する機能。

### 12.10 LIFFとLINEトークの記録導線 【最新】

- 記録導線の主軸は、LIFFに一本化する方向とする。
- 既存のLINEトーク経由の記録機能（番号選択による記録、写真の後付け）は、新しい仕組みへの移行が完了したあとに終了する予定。
- 「使い方」などへのボットの返信は、当面残す。
- 新しい仕組みは、今の `liff/index.html` とは別の検証用ページで確認してから、通常の導線を切り替える。

### 12.11 利用者ごとのGoogleアカウント連携（B-2） 【保留（設計案）】

> 本節は開発ライン (2)「マルチユーザー化・認証基盤」に属する（2.1節）。そだログの主目的である記録体験の改善（ライン (1)）そのものではなく、その成果を他の利用者にも安全に提供するための基盤である。
>
> この節は2026-09-26時点の**設計案**であり、確定していない。特にセキュリティに関わる方式は、選択肢と理由を示すにとどめ、推奨案も未確定とする。実装（B2-1以降）は、本節の確認・確定後に行う。

#### 12.11.1 目的と前提

- 利用者一人ひとりが自分のGoogleアカウントを連携し、**その人自身のGoogle Drive上に**、アプリがフォルダとスプレッドシートを作成して記録を保存する（12.3節の保存先を利用者ごとに持つ）。
- 利用者はLINEユーザーとして識別し（LIFFのIDトークンで確認）、それにGoogleアカウントを1つ結びつける。
- スコープは今と同じく `drive.file`・`openid`・`userinfo.email` だけとする。
- 現在の開発者1人用の構成（12.11.8節）は、この仕組みを作るための検証用であり、最終形ではない。

#### 12.11.2 全体の流れ（案）

```
[LINEアプリ内のLIFF]
 1. 利用者が「Googleと連携する」を押す
 2. LIFF → Cloud Run  POST /api/google/link-tickets
      （Authorization: LIFFのIDトークン。サーバーがLINEで検証し、LINEユーザーIDを特定）
 3. Cloud Run：1回限り・短時間有効の「連携チケット」を発行
      Firestoreには、チケットのハッシュ値とLINEユーザーIDと有効期限だけを保存
      LIFFへ「連携開始URL」を返す（https://…/oauth/start?ticket=…）
 4. LIFF：liff.openWindow({ url, external: true }) で端末の標準ブラウザを開く

[外部ブラウザ（Safari / Chrome など）]
 5. Cloud Run  GET /oauth/start?ticket=…
      チケットを検証して「使用済み」にする（1回限り）
      確認画面：「LINEアカウント（表示名）とGoogleアカウントを連携します」→［続ける］
 6. Cloud Run：state と PKCE を作り、Googleの同意画面へ移動
 7. 利用者がGoogleアカウントを選び、同意する（Drive の項目にチェック）
 8. Google → Cloud Run  GET /oauth/callback?code=…&state=…
      state を検証（1回限り）→ そこに結びついたLINEユーザーIDを取り出す
      認可コードをトークンに交換 → GoogleのIDトークンを検証
 9. Firestoreの users/{LINEユーザーID} に連携情報を保存（refresh tokenは暗号化。12.11.7節）
10. 利用者のDriveに保存先（フォルダ・スプレッドシート・「記録」「場所」タブ）を作成し、
      そのIDをFirestoreに記録（何度実行しても1組だけ。12.3節と同じ方式）
11. 完了画面：「連携しました（Google：a***@gmail.com）」「LINEに戻る」ボタン

[LINEアプリ内のLIFF]
12. 利用者がLINEに戻る → LIFFが GET /api/google/status で連携状態を再取得
      連携済みなら、場所の登録（10章）に進む
```

- 追加が想定されるルート：`POST /api/google/link-tickets`、`GET /api/google/status`、`POST /api/google/unlink`。既存の `/oauth/start`・`/oauth/callback` は、チケット方式に作り替える。
- いずれも新しいルート、または既存のOAuth検証用ルートの変更であり、LINE Webhook（`/webhook/line`）とGASの処理には触れない。

#### 12.11.3 外部ブラウザが必要な理由

- LIFFは、LINEアプリに組み込まれたブラウザ（WebView）の中で動く。
- Googleは、アプリに組み込まれたブラウザからのOAuthログインを**セキュリティ上の理由で拒否する**（`disallowed_useragent` エラー）。組み込みブラウザでは、アプリ側がパスワード入力を盗み見られる可能性を排除できないためである。
- そのため、Googleとの連携の部分だけは、`liff.openWindow({ external: true })` で**端末の標準ブラウザ**を開いて行う必要がある。
- 外部ブラウザにはLINEのログイン状態やLIFFのIDトークンが引き継がれない。そのため、「このブラウザで行う連携は、どのLINEユーザーのものか」を別の方法で安全に伝える必要がある（12.11.4節）。

#### 12.11.4 LINEユーザーとGoogleアカウントを安全に結びつける方法

**選択肢**

| 方式 | 内容 | 評価 |
| --- | --- | --- |
| (a) LIFFのIDトークンをURLに付けて外部ブラウザへ渡す | `…/oauth/start?id_token=…` | **採用しない**。IDトークンは有効期間中に何度でも使え、ブラウザの履歴・ログ・共有URLに残ると、なりすましに使われるおそれがある |
| (b) LINEユーザーIDをURLに付けて渡す | `…/oauth/start?line_user_id=…` | **採用しない**。誰でもURLを書き換えて、他人のLINEユーザーIDで連携できてしまう |
| (c) **1回限り・短時間有効の連携チケット**（推奨案） | LIFF側で本人確認を済ませたあとに、サーバーが推測できない乱数のチケットを発行し、外部ブラウザにはチケットだけを渡す | チケットだけでは何もできず、1回使うと無効になり、数分で期限が切れる |
| (d) 外部ブラウザでLINEログインをやり直す | 外部ブラウザでLINEログインしてからGoogleへ | 確実だが、利用者の操作が1段増え、外部ブラウザでのLINEログインに慣れていない人がつまずく |

**残るリスクと対策（チケット方式の場合）**

- **連携の乗っ取り（他人のチケットのURLを踏ませる攻撃）**：攻撃者が自分のLINEアカウントで発行したチケットのURLを利用者に送り、利用者がそれを開いて自分のGoogleアカウントで同意すると、**利用者のGoogleが攻撃者のLINEアカウントに結びついてしまう**。
  - 対策の候補：チケットの有効期限を短くする（例：5分）／Googleへ進む前に「どのLINEアカウント（表示名）と連携するか」を表示して確認させる／連携後、LIFF側に「連携中のGoogleアカウント（メールアドレスの一部）」を表示し、解除もできるようにする。
  - どこまで対策するか（確認画面を必須にするか、表示名をどこから取得するか）は未確定。
- **チケットのURLが外部ブラウザの履歴に残る**：1回使った時点で無効になり、有効期限も短いため、影響は限定的。応答に `Referrer-Policy: no-referrer` を付け、ログにチケットを出さない。

#### 12.11.5 チケットと `state` の役割

| | 連携チケット | OAuthの `state` |
| --- | --- | --- |
| 役割 | 「この外部ブラウザでの連携は、LIFFで本人確認したどのLINEユーザーのものか」を伝える | 「Googleから戻ってきた応答が、このサーバーが開始した連携に対するものか」を確かめる（CSRF対策）。LINEユーザーIDとPKCEの値に結びつける |
| 発行するタイミング | LIFFで「連携する」を押したとき（手順2〜3） | `/oauth/start` でチケットを使ったとき（手順6） |
| 有効期限の案 | 5分 | 10分 |
| 使える回数 | 1回（使った時点で無効） | 1回（callbackで使った時点で無効） |
| 保存方法の案 | Firestoreに**ハッシュ値のみ**保存。チケット自体は保存しない | Firestoreにハッシュ値・LINEユーザーID・PKCEの検証値を保存。あわせて、同じブラウザから戻ってきたことを確かめるため、HttpOnlyのクッキーにも結びつける |
| 片付け | FirestoreのTTL（有効期限による自動削除）で消す | 同左 |

- 今のSTEP 3の実装では、`state` とPKCEの値をクッキーだけで持ち、保存先を1人に固定している。利用者ごとの連携では、`state` に「どのLINEユーザーか」を結びつける必要があるため、サーバー側（Firestore）にも記録を持つ形に変える。

#### 12.11.6 Firestoreに保存する情報／保存しない情報（案）

**保存する情報**

| コレクション | 項目 | 用途 |
| --- | --- | --- |
| `users/{LINEユーザーID}` | GoogleのユーザーID（`sub`） | 連携先の特定。別のGoogleアカウントに付け替えたかどうかの判定 |
| | Googleのメールアドレス | 「連携中：a***@gmail.com」と表示するため（全部保存するか、一部を伏せて保存するかは未確定） |
| | **暗号化したrefresh token**、暗号鍵のバージョン | 利用者のDriveやSheetsにアクセスするため（12.11.7節） |
| | 許可されたスコープ | `drive.file` が外されていないかの確認 |
| | 保存先：フォルダID・スプレッドシートID・スキーマのバージョン | 毎回Driveを検索しないで済むようにするため（`appProperties` での検索は復旧用として残す） |
| | 連携状態（連携済み／再連携が必要／解除済み）、連携日時、更新日時 | 画面表示と再連携の案内 |
| `linkTickets/{チケットのハッシュ値}` | LINEユーザーID、有効期限、使用済みかどうか | 12.11.5節 |
| `oauthStates/{stateのハッシュ値}` | LINEユーザーID、PKCEの検証値、有効期限 | 12.11.5節 |

**保存しない情報**

- アクセストークン（有効期限1時間。サーバーのメモリ上でだけ使う）
- LIFFやGoogleのIDトークン、認可コード（その場で検証して捨てる）
- チケットや `state` そのもの（ハッシュ値だけを保存する）
- **記録の中身（場所名・作業・メモ・写真など）**。これらは利用者自身のSheetsとDriveにだけ保存し、アプリ側には持たない
- LINEの表示名やプロフィール画像（必要なときにその場で取得する）
- パスワード類（そもそも受け取らない）

#### 12.11.7 refresh tokenの保存方法（選択肢）

refresh tokenがあれば、その利用者のDriveにある「アプリが作ったファイル」を読み書きできる。そのため、漏えい時の影響が最も大きい情報として扱う。

| 方式 | メリット | デメリット |
| --- | --- | --- |
| (A) Firestoreに暗号化せず保存（Google側の保存時暗号化とIAMに任せる） | 実装が最も簡単 | Firestoreを読める権限があれば、そのままトークンを取り出せる。**今の実行アカウントはプロジェクト全体の「編集者」権限を持っているため**、影響範囲が広い。データのエクスポートやバックアップからも漏れうる |
| (B) Firestoreにアプリ側で暗号化して保存（AES-256-GCM）。暗号鍵はSecret Managerに置く | データベースだけが漏れても、トークンは使えない。追加費用がほぼない | 鍵の管理（ローテーション、旧鍵での復号）を自分で実装する必要がある。アプリ自体が侵害されると、鍵とデータの両方に届く |
| (C) FirestoreにCloud KMSで暗号化して保存（エンベロープ暗号化） | 鍵がKMSの外に出ない。復号の操作がすべて監査ログに残る。鍵のローテーションをGoogleが管理し、「復号できる権限」を実行アカウントだけに絞れる | 設定の手間が増える。KMSの費用がかかる（鍵1つあたり月数十円程度＋操作回数に応じた課金。個人〜小規模なら少額の見込み）。復号のたびに通信が発生するため、短時間のキャッシュが必要 |
| (D) 利用者ごとにSecret Managerのシークレットを作る | 利用者ごとに権限を分けられる | シークレットの数が利用者数に比例して増え、費用・上限・権限の管理が煩雑になる。利用者ごとのデータを入れる用途には向かない |

- **推奨案（未確定）**：一般公開を前提とするなら (C)、限定したテスト運用の間は (B) でも可。どちらを選ぶ場合も、暗号化・復号の処理を1か所にまとめ、あとから (B) から (C) へ切り替えられる形にする。
- **どの方式を選んでも必要なこと**：Cloud Runを**専用の最小権限サービスアカウント**に切り替える（今の既定のアカウントはプロジェクト全体の編集者権限を持つ。この切り替えはすでに別STEPで予定している）。
- 連携を解除したときは、Googleのトークン取り消しAPIでrefresh tokenを無効にしてから、Firestoreのデータを消す。利用者のDriveにある記録やファイルは、利用者自身のものなので削除しない。

| 植物名 | 入力欄は1つ（文字列）。「全体」という仮の植物名があった | JSON配列のタグ。タグなし＝場所全体。「全体」タグは作らない |
| 場所の入力 | 場所（庭／室内／その他）×詳細場所の固定2段選択 | 場所名を自由に登録（名前だけで成立）。詳細場所は廃止方向 |
| 場所選択の入口 | 「最近使った場所」3〜5件を代表写真付きカードで表示 | 場所名だけのコラージュ風タイル、登録順で固定表示 |
| 場所の代表写真 | 場所ごとに最新の記録写真を代表写真にする | 持たない |
| 場所の自由登録 | Phase B（STEP 13）で代表写真付き | 名前だけで登録できる機能を前倒しする |
| 記録の成立条件 | 旧LIFFは植物名・作業内容が必須。STEP 9以降は場所以外が任意で、空の記録も確認のうえ保存できた | 場所＋（写真・作業・植物タグ・メモのどれか1つ以上） |
| 写真の添付 | 記録を保存したあと、30分以内にLINEトークで送る | 記録画面で選び、1回の保存で一緒に保存する（開発中） |
| 保存先 | 開発者のDriveにある `garden_log` と写真フォルダ | アプリが作成した新しいフォルダ・シート（旧データは残す） |
| 日付の保存 | `2026/09/25` 形式（Sheetsが日付型に変換する場合あり） | 保存はISO形式、表示は `2026/09/25` |
| 記録の導線 | LIFFとLINEトーク（番号選択・1行テキスト）の併用 | LIFFに一本化する方向。トークでの記録は移行完了後に終了予定 |
| 育成拠点 | 入力項目、のちに「自宅」固定で自動保存 | 新しいシートには持たない |
| アルバムの取得件数 | 旧仕様書では直近50件 | 実装は最大1000件（16章）。新しいアルバムの仕様は【保留】 |

## 16. 現行コードの調査状況

現行（本番稼働中）のLIFF・GASについての調査状況。根拠となるファイル・関数を併記する。

| # | 項目 | 状況 | 要点 |
| --- | --- | --- | --- |
| 1 | 現在の場所選択UIの実装 | 調査済み（9/25） | `liff/index.html` の `loadLocationPicker` / `renderLocationPicker`。過去の記録から「場所＋詳細場所」の組み合わせを最大5件、代表写真付きのカードで表示する。「この場所以外に記録する」を押すと、旧来のセレクト（庭／室内／その他＋詳細場所）に戻る |
| 2 | 場所写真の読み込み箇所 | 調査済み（9/25） | `buildLocationSummaries` の `representativeImage`（その場所の最新の記録写真）を、`loadGroupThumbnail` がGASの `action=image` で読み込む。場所を選んだあとのカード（`applySelectedLocation`）でも同じ画像をもう一度読み込んでいる |
| 3 | 写真読み込みが遅い原因 | コード上の推定は調査済み／**実測は調査予定** | 推定される原因：場所一覧の表示自体がGASの `action=list`（全件取得）の完了を待っている。`action=image` が元サイズの画像をbase64で返す。画像1枚ごとにシート全行を走査して所有者を確認している。GASの呼び出しには1回ごとの固定の遅れがある。実機での計測はまだ |

| 5 | 場所名だけのコラージュUIへ変更する影響範囲 | 調査済み（9/25） | 今のLIFFで行う場合は `liff/index.html` だけで対応できる。新方針では、新しい保存先の「場所」タブをもとに、検証用ページで新しく実装する（STEP 4-2） |
| 6 | 場所選択から記録画面への今の遷移 | 調査済み（9/25） | 起動 → 先にフォームを表示 → `action=list` 完了後に場所カードへ切り替え → タップ → フォーム → 確認画面 → `liff.sendMessages` でLINEへ送信 → 写真はトークで後から送る。LIFFの画面2つとトーク操作が必要 |
| 7 | 現在の植物データ構造 | 調査済み（9/25） | `garden_log` のE列「植物名」。1つの文字列で、STEP 9以降は任意。アルバムは植物名でグループ化し、空欄は「植物名未設定」として表示 |
| 8 | 植物タグ化との差分 | 調査済み（9/25）／**実データの件数は調査予定** | 旧データは1つの文字列で、「全体」という値がある（旧仕様書では13行、実データは未確認）。新方式ではJSON配列を使う。旧データは変換しない（12.8節） |
| 9 | 現在の詳細場所の利用箇所 | 調査済み（9/25）／**実データは調査予定** | 使われている箇所：`garden_log` のD列、LIFFのセレクト、送信テキストの3番目の項目、Driveの保存フォルダ（場所/詳細場所/年）、アルバムの場所グループの判定、作業チップの頻度集計、トークの番号選択フロー、`user_sessions`。トークの番号選択では「庭・北側」が 育成拠点＝庭・場所＝北側 として保存され、LIFFとは列の意味がずれる。該当する行の件数は未確認 |
| 10 | 現在のGoogle Driveの写真保存構造 | 調査済み（9/25） | `IMAGE_FOLDER_ID/場所/詳細場所（空なら「未設定」）/年/`。ファイル名は `YYYYMMDD_植物名_作業内容_NN.拡張子`。`garden_log` のH列にファイルURL、I列にフォルダURL。写真はトークで送った画像のみ（1記録1枚、保存から30分以内） |
| 11 | アルバムの写真取得方法 | 調査済み（9/25） | GASの `doGet` の `action=list`（最大1000件、記録日時の新しい順）で一覧を取り、`action=image` で画像を1枚ずつbase64のJSONとして取得する。LIFFのIDトークンの検証結果は5分間キャッシュされる |
| 12 | 「最近使った場所」機能の実装状況 | 調査済み（9/25） | STEP 8で実装済み、本番で稼働中。新方針では場所タイルを登録順で固定するため、新しい仕組みには引き継がない |
