# LIFFアルバム機能 仕様書

**ステータス: STEP 1〜6 すべて実装・本番デプロイ済み(2026-08-23)。STEP 6の「最近の記録」削除のみ、本番での最終確認待ち**

## 目的

LIFFのメニューを3つ(①記録する／②アルバム／③相談)にし、②アルバムで、これまでLINEから記録してGoogleスプレッドシート・Google Driveに保存した園芸記録を振り返れるようにする。

将来构想の③相談(AI診断)は今回のスコープに含めないが、タブの入れ物だけ用意し、「準備中」であることが分かる形にしておく。

## 前提

- 現在は開発者本人専用のMVP。LINEアカウント・Googleアカウントともに本人のものだけを使う(第三者への一般公開はしていない)。
- そのため、今回のアルバム機能も「本人の記録だけを、本人だけが見られる」ことを前提にする。一般公開時のマルチユーザー対応(利用者ごとのスプレッドシート/Drive、Webhook署名検証など)は別スコープとする。
- データソースは新設せず、既存の `garden_log` シート([00_Config.gs](../gas/00_Config.gs))をそのまま読み取り元とする。

```text
HEADER = [
  "記録日時", "作業日", "場所", "詳細場所", "植物名",
  "作業内容", "メモ", "画像URL", "DriveフォルダURL",
  "LINEユーザーID", "育成拠点",
]
```

## 今回やること／やらないこと

**やること**

- LIFFに②アルバム画面を追加する
- `garden_log` の記録を、日付の新しい順の一覧で表示する
- 写真の有無に関わらず、すべての記録を表示する(写真がない記録はプレースホルダー表示)
- 記録の読み取り専用API(GAS)を新設する

**やらないこと**

- 既存の①記録する機能(LINEメッセージ送信→Webhook→スプレッドシート保存)には一切手を加えない
- ③相談(AI診断)の中身は作らない。タブの器だけ用意する
- 複数ユーザー対応、Googleアカウント連携によるユーザーごとのスプレッドシート/Drive分離は行わない

## 画面構成

LIFF(`liff/index.html`)内に、タブ切り替えで3画面を持たせる。ページ遷移ではなく、既存の `formScreen` / `confirmationScreen` と同様、表示・非表示の切り替えで実装する。

```text
┌─────────────────────────┐
│ ① 記録する │ ② アルバム │ ③ 相談 │  ← タブ
├─────────────────────────┤
│                         │
│      各タブの画面        │
│                         │
└─────────────────────────┘
```

- ①記録する: 既存の入力フォーム(変更なし)
- ②アルバム: 今回追加する一覧画面
- ③相談: 「準備中です」の案内のみを表示するプレースホルダー画面(タップできるが機能はない)

### ②アルバム画面

- 開くと同時に、本人の記録一覧をAPIから取得して表示する
- 1件ごとに次を表示するカード形式(既存の `.card` デザインに合わせる)
  - 作業日
  - 場所 / 詳細場所
  - 植物名
  - 作業内容
  - メモ(あれば)
  - 写真(あれば。タップで拡大表示。なければ「写真なし」のプレースホルダー)
- 初期表示は直近50件。それ以上の過去記録の追加読み込み(もっと見る)は今回のMVPでは対応しない(件数が増えてきたら次のフェーズで対応)
- 読み込み中・0件・取得失敗の状態表示を用意する

## 技術仕様

### API設計

GASの `doGet` は1プロジェクトに1つしか定義できないため、既存の [01_Webhook.gs](../gas/01_Webhook.gs) にある `doGet`(現状はブラウザ確認用の固定文言を返すだけ)を、`action` パラメータで分岐する形に拡張する。

```text
GET {WebアプリURL}?action=list&idToken=...
GET {WebアプリURL}?action=image&fileId=...&idToken=...
```

| action | 用途 | 返り値 |
|---|---|---|
| (未指定) | 従来通りのブラウザ確認 | 既存の固定文言(変更なし) |
| `list` | アルバム一覧取得 | 記録の配列(JSON) |
| `image` | 画像取得プロキシ | 画像バイナリ |

`action=diagnose` のような将来の追加を見越して、実装は if/switch で分岐を足しやすい形にしておく。

### 認証

既存の [09_Liff.gs](../gas/09_Liff.gs) にある `verifyLiffIdToken()` / `isAllowedLiffUser()` をそのまま再利用する(①記録するのLIFF保存で使っているものと同じ仕組み)。

1. LIFF側で `liff.getIDToken()` を取得し、APIリクエストに付与する
2. GAS側でLINEプラットフォームにIDトークンを問い合わせて検証する
3. 検証済みユーザーIDが `ALLOWED_LINE_USER_ID` と一致する場合のみデータを返す
4. 一致しない場合は空配列・エラーを返す(そもそも今は本人しか使わない前提だが、念のため既存の仕組みに揃える)

### 画像の扱い

Google Driveのファイル共有設定を「リンクを知っている全員」に変更して直接読み込む方法は取らない。庭や自宅が写った個人の写真が、そのURLを知っていれば誰でも見られる状態になってしまうため。

代わりに、`action=image&fileId=...` へのリクエストをGAS側で受け、IDトークンを検証したうえで `DriveApp.getFileById(fileId).getBlob()` の内容をそのまま返す**プロキシ方式**にする。Driveの共有設定は非公開のままにできる。

この方式は、将来の③相談(AI診断)で「保存済みの写真をAIに渡して診断する」場合にも、同じ画像取得の経路をそのまま使い回せる。

### 一覧取得(`action=list`)の処理

1. IDトークンを検証する
2. `garden_log` シートの全行を読み取り、`LINEユーザーID` 列が本人のものだけに絞り込む
3. `記録日時` の降順に並べ替える
4. 直近50件を、以下の形に整形して返す

```json
[
  {
    "workDate": "2026/07/10",
    "place": "庭",
    "detailPlace": "北側",
    "plant": "アジサイ",
    "task": "開花",
    "memo": "",
    "hasImage": true,
    "imageFileId": "xxxxxxxx"
  }
]
```

`imageFileId` は `画像URL` 列(Driveの `file.getUrl()` 形式)からIDを抽出して渡す。フロント側は写真が必要なカードだけ `action=image&fileId=...` を追加で呼び出す(一覧取得時に画像本体をまとめて返すと重くなるため)。

## STEP 6: トークルームのリッチメニューを3タブに合わせる(実装・本番反映済み)

### 背景

現状は、トークルーム下部のリッチメニューに「記録する」ボタンが1つだけあり、そこからLIFFを開いた後に、LIFF内のタブで①②③を選び直す2段階の導線になっている。実機動画で確認したところ、リッチメニュー自体を①②③に対応させた方が導線として自然、との判断になった。

### 現状のリッチメニュー構成([08_RichMenu.gs](../gas/08_RichMenu.gs))

3分割、各833px幅。

| ボタン | 種類 | 内容 |
|---|---|---|
| 記録する | uri | `https://liff.line.me/2010871516-DJ2YSRIw` を開く |
| 最近の記録 | message | 「最近の記録」というテキストを送信(既存のトーク内履歴表示機能を呼び出す) |
| 使い方 | message | 「使い方」というテキストを送信(既存のヘルプ表示機能を呼び出す) |

### 変更後のリッチメニュー構成(案)

| ボタン | 種類 | 内容 |
|---|---|---|
| 記録する | uri | `https://liff.line.me/2010871516-DJ2YSRIw?tab=record` |
| アルバム | uri | `https://liff.line.me/2010871516-DJ2YSRIw?tab=album` |
| 相談 | uri | `https://liff.line.me/2010871516-DJ2YSRIw?tab=consult` |

- 「使い方」ボタンはリッチメニューから削除する。トーク内のテキストコマンド「使い方」自体は今回は残す(削除するとヘルプへの導線が完全になくなるため)。別の置き場所は今回のスコープ外で、別途検討する。
- 「最近の記録」は**機能ごと削除し、アルバムに一本化する**(確定)。リッチメニューのボタンだけでなく、トーク内のテキストコマンド(「最近の記録」「最近」「履歴」と送ると履歴が返る機能)自体も削除する。

### 「最近の記録」削除の対象コード(確認用メモ)

現時点のコードを見た限り、「最近の記録」機能は以下に散らばっている。実装時はこれらすべてが対象になる想定。

- [gas/01_Webhook.gs](../gas/01_Webhook.gs): `handleTextMessage` 内の `"最近の記録" / "最近" / "履歴"` のテキストトリガー分岐。あわせて、入力形式エラー時の案内文にある「最近の記録を見る場合は、「最近の記録」と送ってください。」の文言。
- [gas/05_HelpHistory.gs](../gas/05_HelpHistory.gs): `replyHelpMessage()` 内の「【最近の記録を見る】」の案内文。`getRecentGardenLogs()` / `replyRecentGardenLogs()` は、削除すると使用箇所がなくなる。
- [gas/08_RichMenu.gs](../gas/08_RichMenu.gs): リッチメニューのボタン定義(STEP 6の変更に含まれる)。

### 必要な変更

1. **`liff/index.html`**: 起動時にURLのクエリパラメータ(`?tab=record` / `?tab=album` / `?tab=consult`)を読み取り、該当タブを最初から表示する。パラメータがない場合は、これまで通り「記録する」を初期表示にする(後方互換)。
2. **`gas/08_RichMenu.gs`**: `createMyGardenLabRichMenu()` の3エリアの `action` を新しい内容(記録する／アルバム／相談)に変更する。
3. **「最近の記録」機能の削除**: 上記「削除の対象コード」に挙げた箇所を削除・整理する。
4. **リッチメニュー画像の作り直し(コード外の作業)**: 現在のリッチメニュー画像(`RICH_MENU_IMAGE_FILE_ID` で指定しているPNG)には「記録する／最近の記録／使い方」の文字がデザインとして描き込まれている。ボタンの意味を変える場合、**この画像自体を「記録する／アルバム／相談」のデザインで作り直してGoogle Driveへアップロードし直す必要がある**(コード変更だけでは見た目のラベルは変わらない)。ユーザー側でChatGPTに依頼して用意する予定(2026-08-23時点で未着手、できあがり次第共有)。
5. 画像を差し替えたら `setupRichMenu()` を実行してリッチメニューを再設定する(実行には確認を挟む)。

### 進め方

リッチメニュー画像ができあがるまで本番のリッチメニュー切り替え(`setupRichMenu()` の実行)はできないが、それ以外(1〜3)は画像を待たずに着手できる。画像が届き次第、4〜5を行う想定。

### 影響範囲

- `doPost`、記録の保存ロジック(スプレッドシート・Drive保存)そのものには触れない
- 「最近の記録」機能の削除は、これまで動いていたテキストコマンドが使えなくなる変更のため、既存機能への影響として明確に認識しておく
- `setupRichMenu()` の実行(本番のリッチメニュー切り替え)は、実際にLINE利用者全員に見た目が変わる操作のため、事前に確認を取ってから実行する

### 確認事項(確定)

- 最近の記録: 機能ごと削除し、アルバムに一本化する
- リッチメニュー画像: ユーザーがChatGPTに依頼して用意する。できあがり次第共有してもらう
