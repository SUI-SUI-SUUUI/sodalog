# LIFFアルバム機能 仕様書

**ステータス: STEP 1〜7 実装・本番デプロイ済み(直近: 2026-09-06)。STEP 8以降(「場所が主役、植物はタグ」への設計転換)は設計確定・実装未着手。次はSTEP 8から着手する**

## 目的

LIFFのメニューを3つ(①記録する／②アルバム／③相談)にし、②アルバムで、これまでLINEから記録してGoogleスプレッドシート・Google Driveに保存した園芸記録を振り返れるようにする。

将来构想の③相談(AI診断)は今回のスコープに含めないが、タブの入れ物だけ用意し、「準備中」であることが分かる形にしておく。

## 前提

- 現在は開発者本人専用のMVP。LINEアカウント・Googleアカウントともに本人のものだけを使う(第三者への一般公開はしていない)。
- そのため、今回のアルバム機能も「本人の記録だけを、本人だけが見られる」ことを前提にする。一般公開時のマルチユーザー対応(利用者ごとのスプレッドシート/Drive、Webhook署名検証など)は別スコープとする。
- データソースは新設せず、既存の `garden_log` シート([00_Config.gs](../gas/00_Config.gs))をそのまま読み取り元とする。

```text
HEADER = [
  "記録日時", "作業日", "場所", "詳細場所", "植物名",
  "作業内容", "メモ", "画像URL", "DriveフォルダURL",
  "LINEユーザーID", "育成拠点",
]
```

## 今回やること／やらないこと

**やること**

- LIFFに②アルバム画面を追加する
- `garden_log` の記録を、日付の新しい順の一覧で表示する
- 写真の有無に関わらず、すべての記録を表示する(写真がない記録はプレースホルダー表示)
- 記録の読み取り専用API(GAS)を新設する

**やらないこと**

- 既存の①記録する機能(LINEメッセージ送信→Webhook→スプレッドシート保存)には一切手を加えない
- ③相談(AI診断)の中身は作らない。タブの器だけ用意する
- 複数ユーザー対応、Googleアカウント連携によるユーザーごとのスプレッドシート/Drive分離は行わない

## 画面構成

LIFF(`liff/index.html`)内に、タブ切り替えで3画面を持たせる。ページ遷移ではなく、既存の `formScreen` / `confirmationScreen` と同様、表示・非表示の切り替えで実装する。

```text
┌─────────────────────────┐
│ ① 記録する │ ② アルバム │ ③ 相談 │  ← タブ
├─────────────────────────┤
│                         │
│      各タブの画面        │
│                         │
└─────────────────────────┘
```

- ①記録する: 既存の入力フォーム(変更なし)
- ②アルバム: 今回追加する一覧画面
- ③相談: 「準備中です」の案内のみを表示するプレースホルダー画面(タップできるが機能はない)

### ②アルバム画面

- 開くと同時に、本人の記録一覧をAPIから取得して表示する
- 1件ごとに次を表示するカード形式(既存の `.card` デザインに合わせる)
  - 作業日
  - 場所 / 詳細場所
  - 植物名
  - 作業内容
  - メモ(あれば)
  - 写真(あれば。タップで拡大表示。なければ「写真なし」のプレースホルダー)
- 初期表示は直近50件。それ以上の過去記録の追加読み込み(もっと見る)は今回のMVPでは対応しない(件数が増えてきたら次のフェーズで対応)
- 読み込み中・0件・取得失敗の状態表示を用意する

## 技術仕様

### API設計

GASの `doGet` は1プロジェクトに1つしか定義できないため、既存の [01_Webhook.gs](../gas/01_Webhook.gs) にある `doGet`(現状はブラウザ確認用の固定文言を返すだけ)を、`action` パラメータで分岐する形に拡張する。

```text
GET {WebアプリURL}?action=list&idToken=...
GET {WebアプリURL}?action=image&fileId=...&idToken=...
```

| action | 用途 | 返り値 |
|---|---|---|
| (未指定) | 従来通りのブラウザ確認 | 既存の固定文言(変更なし) |
| `list` | アルバム一覧取得 | 記録の配列(JSON) |
| `image` | 画像取得プロキシ | 画像バイナリ |

`action=diagnose` のような将来の追加を見越して、実装は if/switch で分岐を足しやすい形にしておく。

### 認証

既存の [09_Liff.gs](../gas/09_Liff.gs) にある `verifyLiffIdToken()` / `isAllowedLiffUser()` をそのまま再利用する(①記録するのLIFF保存で使っているものと同じ仕組み)。

1. LIFF側で `liff.getIDToken()` を取得し、APIリクエストに付与する
2. GAS側でLINEプラットフォームにIDトークンを問い合わせて検証する
3. 検証済みユーザーIDが `ALLOWED_LINE_USER_ID` と一致する場合のみデータを返す
4. 一致しない場合は空配列・エラーを返す(そもそも今は本人しか使わない前提だが、念のため既存の仕組みに揃える)

### 画像の扱い

Google Driveのファイル共有設定を「リンクを知っている全員」に変更して直接読み込む方法は取らない。庭や自宅が写った個人の写真が、そのURLを知っていれば誰でも見られる状態になってしまうため。

代わりに、`action=image&fileId=...` へのリクエストをGAS側で受け、IDトークンを検証したうえで `DriveApp.getFileById(fileId).getBlob()` の内容をそのまま返す**プロキシ方式**にする。Driveの共有設定は非公開のままにできる。

この方式は、将来の③相談(AI診断)で「保存済みの写真をAIに渡して診断する」場合にも、同じ画像取得の経路をそのまま使い回せる。

### 一覧取得(`action=list`)の処理

1. IDトークンを検証する
2. `garden_log` シートの全行を読み取り、`LINEユーザーID` 列が本人のものだけに絞り込む
3. `記録日時` の降順に並べ替える
4. 直近50件を、以下の形に整形して返す

```json
[
  {
    "workDate": "2026/07/10",
    "place": "庭",
    "detailPlace": "北側",
    "plant": "アジサイ",
    "task": "開花",
    "memo": "",
    "hasImage": true,
    "imageFileId": "xxxxxxxx"
  }
]
```

`imageFileId` は `画像URL` 列(Driveの `file.getUrl()` 形式)からIDを抽出して渡す。フロント側は写真が必要なカードだけ `action=image&fileId=...` を追加で呼び出す(一覧取得時に画像本体をまとめて返すと重くなるため)。

## STEP 8以降: 「場所が主役、植物はタグ」への設計転換(検討中・着手前)

### 背景

ハッカソンのメンターとのやり取り([[project_liff_album_feature]] 参照)を経て、そだログを「写真主体の園芸記録管理」として位置づけ直した(STEP 7)。そのうえで改めて振り返ると、今の設計は「1件の記録＝1つの場所＋1つの植物」を前提にしており、次の実態に合っていない。

- ユーザーの庭は広く、数十種類の植物を育てている。植物1つ1つを個別に追いかける運用は、植物の種類が多いほど破綻する。
- 実際の作業は「この花壇の草取りをした」のように、場所・区画単位で複数の植物にまたがって行われることが多い。
- 現状、場所全体の作業は植物名を「全体」という仮の値で入れる運用(デモデータ作成時に採用)で凌いでいたが、これは本来「場所が主役、植物は任意のタグ」という設計をワークアラウンドしていただけだった。
- 一般的な植物管理アプリの多くは「植物を登録して、その植物のお世話を記録する」発想だが、そだログは「庭を場所ごとに見て、その場所の変化を残す」という逆の発想にする。広い庭・植物数が多い人ほど恩恵が大きく、そだログの個性になる。

### 設計方針(確定)

1. **場所(区画)を記録の主語にする。植物名は任意のタグにする。** 1件の記録に、植物タグを0〜複数個つけられる。タグなし(場所全体の作業)、タグ1つ、タグ複数(同じ日に同じ場所で複数の植物を触った)のすべてに対応する。
2. **場所は、今の「場所(庭/室内/その他)×詳細場所(北側/南側/…)」という固定の2段組み合わせをやめ、ユーザーが自分の言葉で登録する自由な名前にする。**(例:「北側の庭」「花壇A」「玄関前」「ベランダ」)。場所の粒度・階層の細かさは人によって違ってよく、そだログ側が「正しい区切り方」を決めない。この変更自体(STEP 13)は影響範囲が大きいため後半に回すが、STEP 8の時点から「場所は `locationId` / `locationName` / `representativeImage` を持つ1つのエンティティ」という形を内部的に意識して作る(下記「STEP 8の設計制約」参照)。これにより、STEP 8で作ったUI・抽出ロジックがSTEP 13で作り直しにならないようにする。
3. **場所以外(写真・作業内容・メモ・植物タグ)はすべて任意にする。ただし完全な空記録は許可しない。** 「場所」は必須。それに加えて「写真・作業内容・メモ・植物タグ」のうち最低1つは入力されていることを保存条件にする。「写真だけ残す」「メモだけ残す」は成立するが、場所だけを選んで他は何も入れずに保存、は不可。
3-1. **作業内容も複数選択できるようにする。**(例:同じ日に草取りをしてから水やりもした、を1件の記録にまとめられる)今のラジオボタン(1つだけ)からチェックボックス(複数可)に変える。実際の作業が複数の内容にまたがることが多いための変更。
4. **記録の入口を「最近使った場所」にする。** ①記録するタブを開いた瞬間に、直近使った場所を3〜5件、代表写真つきのカードで並べる(アルバムの場所カードと同じ見た目)。タップしたら、その場所が選択された状態で記録画面に進む。これがタップ数削減として一番効果が大きいと判断し、最優先にする。
5. **「最近使った植物」は入口ではなく、場所を選んだ後の補助にする。** 植物タグ入力欄に、その場所で過去によく使われたタグを候補チップとして出す(複数選択可、新規タグは自由入力でも追加できる)。
6. **作業内容チップは、場所ごとの使用頻度順に並べる。**(例:西側花壇では「草取り・花がら摘み・水やり」がよく使われるなら、それを上に出し、残りは「その他」にまとめる)表示順の並べ替えなので、STEP 9で複数選択に対応した後、STEP 10で追加する。
7. **植物タグ・作業内容の保存形式はどちらもJSON配列にする。**(例:`["アジサイ","ホスタ"]`、`["草取り","水やり"]`)区切り文字方式(「、」「,」など)は将来値自体に記号が入ると壊れるため採用しない。GAS側は`JSON.stringify`/`JSON.parse`で素直に扱えるため、区切り文字方式からJSONへの移行という二度手間は発生させない。作業内容は他の項目より先にSTEP 9で複数選択対応するため、先にJSON配列化されるのはこちらになる。
8. **「全体」という仮の植物名は廃止する。「植物タグなし」＝「場所全体の記録」に意味を統一する。** 既存のデモデータ13行にある「全体」という値は、STEP 11のデータ移行で「タグなし(空配列)」に変換する。

### STEP 8の設計制約(場所エンティティを見据えた作り方)

STEP 8では、今の「場所+詳細場所」の文字列の組み合わせをそのまま使ってよいが、実装上は次の形に寄せておく。

```js
// 「場所」を、実績データから抽出した1つのオブジェクトとして扱う
{
  locationId: "庭__南側",       // 場所+詳細場所から作る一時的なキー(STEP 13で本物のIDに置き換わる)
  locationName: "庭・南側",     // 表示名
  representativeImage: "xxxxxxxx", // 最新記録の画像ファイルID
}
```

`renderAlbumZones` の `zoneMap` が既にこれに近い形(`place`/`detailPlace`/`count`/`latestDate`/`imageFileId`)を持っているため、そのロジックを流用・共通化する形で実装する。UIコンポーネント(場所カードの描画)も、アルバムと記録フォームの入口で共通の関数にしておくと、STEP 13で「場所」の取得元が実績データからユーザー登録データに変わっても、カードの描画部分は変えずに済む。

### 進め方(確定)

Phase A(記録を速くする、STEP 8〜12)と Phase B(場所管理を作り直す、STEP 13)を完全に分離する。STEP 14は今回のスコープに含めず、完全に後回しにする。

**Phase A: 記録を速くする**

- **STEP 8**: 記録フォームの入口を「最近使った場所」カードに変更(上記「STEP 8の設計制約」に沿って実装)
- **STEP 9**: 記録画面を1画面に統合。場所のみ必須、他は「いずれか1つ以上」を条件に任意化。あわせて作業内容をチェックボックス(複数選択・JSON配列保存)に変更(アルバムの作業内容表示ロジックも配列対応にする)
- **STEP 10**: 作業内容チップを場所ごとの使用頻度順に並べ替え

**→ STEP 8〜10完了後、一度ここで止めて実際に庭仕事をしながら使ってみて、体感の速さを確認する。その結果を見てから先に進む。**

- **STEP 11**: 植物名列をJSON配列の複数タグ対応にする(データモデル変更。「全体」→「タグなし」の移行を含む)
- **STEP 12**: アルバムの植物グルーピングをタグ対応に変更 + 記録フォームに植物タグ選択UIを追加

**Phase B: 場所管理を作り直す**

- **STEP 13**: 場所を、固定の2段選択からユーザー登録制の自由な場所名(代表写真つき)に変更。既存データの移行を含む

**対象外(今回はやらない)**

- **STEP 14**: 作業日の「今日/昨日」ピルなど、細かいタップ数削減の追加施策。今回は見送り

### 確認事項(すべて確定)

- 「何も選ばず保存」: 場所は必須。加えて写真・作業内容・メモ・植物タグのいずれか1つ以上が必須。完全な空記録は不可
- 作業内容はSTEP 9で複数選択に対応する(チェックボックス化)。実際の作業が複数の内容にまたがることが多いため
- 植物タグ・作業内容の保存形式: どちらもJSON配列(例:`["アジサイ","ホスタ"]`、`["草取り","水やり"]`)。区切り文字方式は採用しない
- 「全体」という仮の植物名は廃止し、「タグなし＝場所全体」に統一する。既存のデモデータの移行はSTEP 11で行う
- STEP 13(場所の自由登録制)は今回の大きいスコープに含めるが、Phase Bとして完全に独立させ、Phase A(STEP 8〜12)の後に着手する
- STEP 14は今回のスコープ外
